## Out-of-scope observations

1. **The SKILL.md's wording is slightly ambiguous about whether `N` includes chunks AND retries or just retries.** The CLI docstring says "1 + N retries"; the SKILL.md fallback protocol section also says "1 + N_retries". But the SKILL.md splitting strategy section says "chunk count `N` is recorded in the gate artifact as `Reviewer invocations: N`" — which conflates chunks and retries under the same `N`. In practice the master computes N from both, so the artifact's N reflects total invocations. This is acceptable per the coder's design decision; flagging for future tightening of the SKILL.md wording if needed.

2. **`max_tokens=800` is hard-coded in the test docstring and the SKILL.md, but the `chunk_for_review()` helper accepts it as a parameter.** This is good (testable, future-tunable). The default is 800 in both the test and the SKILL.md examples; nothing forces the value externally. Future tuning (e.g., per-style-guide) is a one-liner change to the call site.

3. **Arabic books: the SKILL.md notes that 800-token budget may be tighter for Arabic (higher tokens-per-word ratio in some tokenizers).** The coder flagged this in their summary as "future tuning". Acceptable for v1; flag for v0.21.0+ discussion.

4. **Default invocation count = 1 (always single-pass) vs. computed-from-chapter-length** — coder flagged this as a discussion point. Currently master must pass `--reviewer-invocations N` explicitly. An alternative would be `gate_summary.py` computing N from chapter length + max_tokens. Master-level control is cleaner for now; flag for future.

5. **Plant test #4 (`--reviewer-invocations 0` not validated):** Adding `argparse` `type=callable_that_rejects_zero` or a post-parse check would catch the degenerate case. Not in spec; recommend adding to a future phase if master ever miscounts. WARN.
