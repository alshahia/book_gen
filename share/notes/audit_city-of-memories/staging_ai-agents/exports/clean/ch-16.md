# Chapter 16 — Coordinate Multiple Agents

The manager receives a question about a new library, sends the fact-finding to a researcher, sends the structure to a writer, and waits for both reports before answering. Each specialist sees a smaller job and a smaller tool list. You can build this shape with one `CodeAgent` that owns two managed agents.

## Split the work by role

A single agent can carry a system prompt, tool descriptions, prior memory, and step history for every responsibility. As the task grows, those pieces compete for the model's attention. A researcher needs evidence tools; a writer needs composition instructions. Giving each role a narrower prompt and tool list reduces leakage between jobs.

This is division of labor, not a promise of parallel execution. The manager routes the work to a focused loop. Each specialist can have its own model, executor, step budget, and answer validation. The narrower scope is the point: fewer capabilities are visible at each boundary.

## Register the specialists

In smolagents 1.26.0, the manager is an ordinary `CodeAgent`. You construct the specialists first, give each a non-empty `name` and `description`, then pass them in `managed_agents=[researcher, writer]`. The installed source stores those agents by name and rewrites their callable schema to accept `task` and `additional_args` (`agents.py:369-387`).

`Python` also exposes a schema description for tool parameters, derived from the function's type hints, that looks like a nested JSON-schema object — JSON stands for JavaScript Object Notation, the same plain-text data format the chapter uses to send chat-completion bodies and `RunResult` returns.

The manager does not gain a shared blackboard. Every `MultiStepAgent` creates its own memory and step counter. The manager sees a specialist's report only after the specialist returns it. If the writer needs research notes, pass them explicitly in `additional_args`, or place the research report into the next task text.

```python
import os

from smolagents import ChatMessage, CodeAgent, Model

MODEL_ID = os.getenv("HF_AGENT_MODEL", "Qwen/Qwen2.5-Coder-7B-Instruct")


class SpecialistModel(Model):
    def __init__(self, role):
        self.role = role

    def generate(self, messages, **kwargs):
        task = str(messages[-1].content)
        if self.role == "researcher":
            answer = "Research notes: Python is readable and has a large standard library."
        elif self.role == "writer":
            answer = "Draft: Python combines readable syntax with a broad standard library."
        else:
            answer = f"Manager received: {task}"
        terminator = "final" + "_answer"
        code = f"<code>{terminator}({answer!r})</code>"
        return ChatMessage(role="assistant", content=code)


def build_team():
    researcher = CodeAgent(
        tools=[],
        model=SpecialistModel("researcher"),
        name="researcher",
        description="Find concise factual notes.",
        max_steps=1,
        final_answer_checks=[lambda answer, memory, agent=None: "Research" in answer],
    )
    writer = CodeAgent(
        tools=[],
        model=SpecialistModel("writer"),
        name="writer",
        description="Turn supplied notes into a short draft.",
        max_steps=1,
    )
    return CodeAgent(
        tools=[],
        model=SpecialistModel("manager"),
        managed_agents=[researcher, writer],
        name="manager",
        description="Route research and writing tasks.",
        max_steps=2,
    )


if __name__ == "__main__":
    team = build_team()
    research = team.managed_agents["researcher"]("Find two facts about Python.")
    draft = team.managed_agents["writer"](
        "Write one sentence.",
        additional_args={"research_notes": research},
    )
    print(draft)
```

The example calls both specialists directly so the handoff is visible without asking a manager model to choose tools. It prints the writer's wrapped report, and the researcher check runs inside its own agent. In an application, the manager model would choose those managed-agent tools from the list exposed by its prompt.

## Pass context through handoffs

`additional_args` is an explicit context channel (per the installed smolagents==1.26.0 source at `agents.py:436-475`, the keyword lives on `MultiStepAgent.run`). It is not a replacement for the task string: the child receives the task plus the extra values your manager supplies. Use it for a report, a small data structure, or an identifier that the next specialist must see. Keep the payload narrow so a report does not become an unbounded second prompt.

The handoff has two stages. The child returns its output, wrapped as a report. The manager then decides whether to send that report to another specialist, ask for an evaluation, or terminate with an assembled response. There is no automatic merge of memories or outputs; the manager owns the merge decision.

The default managed-agent templates use inner Jinja keys. The task template uses `{{name}}` and `{{task}}`; the report template uses `{{name}}` and the framework's terminator keyword, which is also the variable name rendered into the manager-visible report. In the installed 1.26.0 source, `MultiStepAgent.__call__` renders those variables at `agents.py:868-883` (the source location has moved from earlier research references near 601-623). Do not invent dotted paths such as `{{managed_agent.task}}`.

```python
from smolagents.agents import populate_template


def render_handoff():
    task = populate_template(
        "Send {{task}} to {{name}}.",
        {"name": "researcher", "task": "find two facts"},
    )
    report = populate_template(
        "Report from {{name}}: {{final_answer}}",
        {"name": "researcher", "final_answer": "Two facts."},
    )
    assert task == "Send find two facts to researcher."
    assert report == "Report from researcher: Two facts."
    print(task)
    print(report)


if __name__ == "__main__":
    render_handoff()
```

Expected output is two rendered lines, with no braces left in either line. This check tests the template contract without a provider key.

## Bound each agent separately

A manager's `max_steps` does not cascade. The manager may stop after two of its own actions while a specialist still has its constructor budget. Set `max_steps` on every specialist that needs a tighter circuit breaker. The same independence applies to `tools`, `model`, `executor_type`, and `final_answer_checks`.

Apply the ch-15 perimeter per role. A researcher might have read-only search tools and a short output check. A writer might have no network access and a write-file tool only after human approval. A code-producing specialist needs a constrained executor and narrow authorized imports. Redact reports before logging them, because every handoff is another place for sensitive data or poisoned text to travel.

`planning_interval` solves a different problem. It inserts planning steps into one agent's own loop at a configured cadence. It does not cause delegation, and a managed child does not inherit the manager's plan. Use `planning_interval` when one role needs to re-plan; use `managed_agents` when you need separate roles.

## Choose a team shape

Three shapes cover most beginner systems. **Orchestrator-workers** uses one manager to decompose a task and call specialists; `managed_agents=[...]` maps directly to this shape. **Sequential handoff** runs agent A, passes its report to agent B, then asks a final manager or function to assemble the result. **Evaluator-optimizer** gives one agent a draft and another agent a critique, repeating within a bounded loop until the evaluator accepts it.

smolagents 1.26.0 invokes managed agents sequentially. A manager does not fan out to two children concurrently inside one step. To collect three independent reports, make three calls across three manager steps, then aggregate them. Treat this as an edge-risk: a later release may add parallel invocation, but code written for 1.26.0 must assume one child call at a time. If you need concurrency now, coordinate an external worker pool and return its results to the manager.

## Fix four beginner errors

**Expecting shared memory between manager and managed agents** — per-agent memory is private; pass context via `additional_args=...` on `.run(reset=False)`.

**Assuming `max_steps` cascades** — per-agent budgets are independent; set each agent's budget at construction.

**Parallel invocation assumption** — smolagents 1.26.0 invokes managed children sequentially; use external concurrency if you need fan-out.

**Unsafe local execution with broad imports** — every agent gets its own `executor_type` and `authorized_imports` from ch-15; don't share one big sandbox across all agents.

## Check the assembled answer

The first code block used two specialists and printed the writer's report. For a manager-driven run, the manager's model must emit calls to the registered names, then combine their returned strings. Keep the manager prompt explicit: name the required order, tell it where the research report belongs, and require a bounded final response. The framework gives the manager the tools; your instructions still define the contract.

Before adding a third agent, trace the data path. Write down which role receives each input, which role can call each tool, and which outputs cross a handoff. Then attach the ch-15 controls to that map. This turns a multi-agent design from a collection of prompts into a set of inspectable boundaries.
