# Chapter 10 — Give Agents Useful Tools

A terminal opens, `agent.run("how many words in this sentence?")` returns, and the answer lands as a clean integer — no JSON dump, no stringified number, no `None`. The tool returned exactly what its type hint said it would, and the framework passed it through unchanged. This chapter is where that contract becomes the rule you write tools against.

Coming from ch-09: you built a `CodeAgent`, passed your first `@tool` function in `tools=[...]`, and watched the loop call it. This chapter turns that decorator into a typed contract, documents the verified no-auto-coercion return behavior, and walks four beginner errors to avoid.

## Why the decorator is a contract

The `@tool` decorator reads the function's name, parameter type hints, return type hint, and docstring and turns them into a structured description the agent can inspect at every step. The body still does the work; the decoration becomes the agent-facing contract. The decorator is defined in the installed smolagents==1.26.0 source at `tools.py:1061`. Skip a hint or a description and the decorator raises `TypeHintParsingException` at import time, so a half-decorated tool fails loudly.

## The contract: hints, docstring, return

A `@tool` function is a small contract between you and the model. The agent sees the contract, not the body. Three pieces are mandatory.

```python
from smolagents import tool


@tool
def word_count(text: str) -> int:
    """Count whitespace-separated words in a string.

    Args:
        text: The input text to count words in.
    """
    return len(text.split())
```

Type hints on every parameter are not optional decoration. The decorator reads them via `get_json_schema()` in `smolagents._function_type_hints_utils.py` to build the JSON schema sent to the model; the schema is the menu the model reads to decide which arguments are legal.

The docstring does two jobs. The leading description becomes the tool's `description` field, which is the sentence the model reads when deciding whether to pick the tool. The Google-style `Args:` block (or the equivalent NumPy `Parameters` section with a dashed underline) becomes the per-parameter description in the schema.

## Schemas and selection rules

The agent never reads the function body. It sees a menu card built from the type hints and the docstring, and it picks one tool per step from that menu. The card needs a selection rule.

A weak description is "Counts words." A useful description is "Count the number of words in a string. Use this when the user asks how long a piece of text is." The second sentence is the rule that lets the model pick the right tool.

## The no-auto-coercion return behavior

This is the chapter's key correction. A `@tool` returning a Python value returns that value to the agent unchanged. The framework does not silently turn a dictionary into a JSON string, a number into text, or `None` into the empty string. Verified against the installed smolagents==1.26.0 source at `tools.py:231-249` and `agent_types.py:263-281` on 2026-08-01.

The `Tool.__call__` method runs the tool's `forward` and then, only when `sanitize_inputs_outputs=True`, passes the output through `handle_agent_output_types`. That helper tries three concrete types: a `str` becomes `AgentText`, a `PIL.Image.Image` becomes `AgentImage`, and a `torch.Tensor` becomes `AgentAudio`. Anything else — a `dict`, an `int`, a `float`, a `list`, a `None`, a custom dataclass — returns unchanged.

The chapter's rule: return a string unless another type is genuinely useful. When the model needs a JSON text, call `json.dumps(...)` yourself. When it needs a stringified number, call `str(...)` yourself.

```python
import json
from smolagents import tool


@tool
def stats_payload(text: str) -> str:
    """Return a JSON text with word and character counts.

    Args:
        text: The input text to summarize.
    """
    return json.dumps({"words": len(text.split()), "characters": len(text)})
```

The `stats_payload` tool returns a plain Python `str` whose contents happen to be JSON text. Removing the `json.dumps(...)` call would return a `dict`, which the framework would pass through unchanged.

## Pick from the built-in inventory

smolagents 1.26.0 ships nine public built-in tools, verified by inspecting `dir(smolagents)` on 2026-08-01. Importing one does not attach it to your agent; you still pass an instance in `tools=[...]`. The nine built-ins are `DuckDuckGoSearchTool(max_results=10, rate_limit=1.0)`, `VisitWebpageTool(max_output_length=40000)`, `WikipediaSearchTool(user_agent=..., language='en', content_type='text', extract_format='WIKI')`, `WebSearchTool(max_results=10, engine='duckduckgo')`, `SpeechToTextTool`, `PythonInterpreterTool(authorized_imports=None, timeout_seconds=30)`, `FinalAnswerTool`, `UserInputTool`, and `ApiWebSearchTool(endpoint='', api_key='', api_key_name='', headers=None, params=None, rate_limit=1.0)`.

The choice rule is to import only the built-in you actually need. `DuckDuckGoSearchTool` is the beginner default for search; `WikipediaSearchTool` is safer for a single canonical source; `VisitWebpageTool` is the read-it-back half of the search-and-fetch pair. `PythonInterpreterTool` is mostly redundant with `CodeAgent`. The built-in terminator `FinalAnswerTool` is added to every agent's tool list via `setdefault`.

## The base-tool shortcut and its default

There is one shortcut for adding a small default set of built-ins: `add_base_tools=True`. The kwarg is inherited through `**kwargs` by both `CodeAgent` and `ToolCallingAgent`, and its default is `False`. When set to `True`, the agent receives `python_interpreter`, `web_search` (a `DuckDuckGoSearchTool`), and `visit_webpage` through `TOOL_MAPPING`. The built-in terminator tool is added regardless of the flag's value.

`CodeAgent` already executes model-written Python, so the shortcut does not add `python_interpreter` to it; `ToolCallingAgent` does not, so the shortcut adds `python_interpreter` to its tool list. The beginner rule is to use `tools=[...]` so the agent's capability surface is visible.

## Vague docstrings, missed selections

The model picks a tool by reading its name, description, and input schema, not the function body. A vague docstring tells the model nothing to distinguish your tool from the agent's own Python execution.

The first example says "Look up a number." The second says "Look up the population of a country by name. Use this when the user asks for a current population figure." The same code body, the same return type, the same arguments — but the second description gives the model a selection rule.

## Tool errors are feedback, not termination

A `ToolCallingAgent` invokes a tool as a normal Python call. If the tool raises, smolagents catches the underlying exception, wraps it as `AgentToolExecutionError` with the tool name, supplied arguments, exception type and message, and guidance to fix the call, then feeds that error back into the current step and continues the loop. The model sees the wrapped error and may retry with corrected arguments or pick a different tool.

Inside a tool, catch expected network and file errors and return a concise recovery message; raise only for genuinely unexpected failures.

## The sandbox is not a safety wall

A `@tool` function is ordinary Python. It can close over variables, mutate globals, read and write files, send network requests, or call subprocesses. `ToolCallingAgent` calls tools in the host process with the full authority of the user's Python; `CodeAgent` registers tools inside its configured Python executor. The default executor is `LocalPythonExecutor`, which AST-restricts model-generated code but still trusts the user's tool implementations.

The chapter's rule is to keep beginner tools read-only or harmless; real isolation — the `executor_type="docker"` knob, the `authorized_imports=` whitelist, and the `final_answer_checks=` gate — is the topic of ch-14.

## Four beginner errors

These four failures appear before any advanced feature. Name the failure, then apply the smallest fix.

1. **Missing type hints or argument descriptions.** The decorator cannot build a schema, so it raises `TypeHintParsingException` at import time. Fix: add a type hint to every parameter and an `Args:` entry to every parameter.

2. **Vague docstring.** The agent skips the tool and falls back to its own Python, or the loop runs longer than expected without producing an answer. There is no traceback. Fix: write a specific docstring with a one-line description and a "use this when…" sentence, then list each parameter in an `Args:` block.

3. **Returning `None`.** A tool that returns `None` returns actual `None` to the agent, not an empty string. Fix: return a clear success or failure message on every path.

4. **Naming a custom tool that collides with the built-in terminator's name.** The framework's `MultiStepAgent._setup_tools` uses `setdefault`, so the custom tool silently replaces the framework's `FinalAnswerTool`. Fix: pick a different name. Duplicate names among explicitly supplied tools raise `ValueError`, but a single collision with the built-in terminator's name is not rejected.

## Extend the ch-09 agent with two tools

The smallest runnable extends the ch-09 agent rather than introducing a new class. The runnable defines two typed `@tool` functions with different return types, passes them in `tools=[...]`, and calls `.run()`.

```python
import json
import os

from smolagents import CodeAgent, InferenceClientModel, tool


@tool
def word_count(text: str) -> int:
    """Count whitespace-separated words in a string.

    Args:
        text: The input text to count words in.
    """
    return len(text.split())


@tool
def stats_payload(text: str) -> str:
    """Return a JSON text with word and character counts.

    Args:
        text: The input text to summarize.
    Use this when the user wants a structured payload.
    """
    return json.dumps({"words": len(text.split()), "characters": len(text)})


def load_api_key(name: str) -> str:
    token = os.getenv(name)
    if not token:
        raise SystemExit(f"Set {name} in .env or your shell.")
    return token


def main():
    load_api_key("HF_TOKEN")
    agent = CodeAgent(
        tools=[word_count, stats_payload],
        model=InferenceClientModel(model_id="Qwen/Qwen2.5-Coder-7B-Instruct"),
    )
    answer = agent.run(
        "Use stats_payload to summarize 'hello world' and print the result."
    )
    print(answer)
    assert isinstance(answer, str), "the agent's reply is a string"


if __name__ == "__main__":
    main()
```

`word_count` returns an `int`, which the framework passes through unchanged. `stats_payload` returns a `str` because the author called `json.dumps(...)` explicitly; the model reads the JSON text in the next observation. The runnable compiles in `E:\book_gen\.venv\Scripts\python.exe`; full execution short-circuits on `load_api_key("HF_TOKEN")` until the reader has a token, the same guard ch-07 and ch-09 taught.

## Check: the dict-return path stays raw

A small check isolates the no-auto-coercion rule. Decorate a tool that returns a dict, call it directly, and observe that the dict is preserved as-is.

```python
from smolagents import tool


@tool
def stats_dict(text: str) -> dict:
    """Return a dict with word and character counts.

    Args:
        text: The input text to summarize.
    """
    return {"words": len(text.split()), "characters": len(text)}


def main():
    result = stats_dict("hello world")
    print(type(result).__name__)
    print(result)
    assert isinstance(result, dict), "no auto-coercion of dict returns"


if __name__ == "__main__":
    main()
```

Expected output:

```text
dict
{'words': 2, 'characters': 11}
```

`handle_agent_output_types` does not touch dicts, so the tool author's return reaches the caller unchanged.

> **The move:** Write a typed, docstring-rich `@tool` function, pass it in `tools=[...]`, and rely on the verified no-auto-coercion tool-return behavior — return a string unless another type is genuinely useful, and call `json.dumps(...)` or `str(...)` explicitly when the model needs text.
