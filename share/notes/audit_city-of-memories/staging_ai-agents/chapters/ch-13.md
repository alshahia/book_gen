# Chapter 13 — Observe, Debug, and Evaluate Runs

The terminal shows a finished run, and you have nothing to look at but the printed answer. A second run does the wrong thing, and you cannot tell which step drifted. The agent saw every step it took, and so can you, if you attach the right hooks and read the right fields afterward.

Coming from ch-12: you built a single-agent workflow with `managed_agents`, attached a `step_callbacks` observer, gated accepted answers with `final_answer_checks`, and mapped six exception classes to recovery actions. This chapter reads the agent's own memory and the framework's run record as evidence while you debug an actual run.

## Name the three observability pillars

Agents fail in three different ways: they did the wrong thing, they did the right thing for the wrong reason, or they did the right thing and produced a bad answer. The framework exposes one hook per failure.

Step callbacks observe what the agent did and in what order. Agent memory and `RunResult` debug why a run went wrong by correlating tool calls with observations. The candidate-answer gate and a small evaluator score how good the answer was.

Each pillar builds on the typed step objects introduced by the previous one, so reading them in order is the path of least resistance. Verified against the installed smolagents==1.26.0 source at `agents.py:436-538` on 2026-08-01.

## Set the verbosity dimmer

`verbosity_level` is the logging dimmer (four levels, not a binary switch) for the agent's built-in console output. Pass the named enum value `LogLevel.INFO` for normal runs, `LogLevel.DEBUG` when a single run has gone wrong, and `LogLevel.OFF` once the agent runs unattended in a script. The default is `LogLevel.INFO`, which prints the standard `New run / Step N / Executing parsed code` boxes.

Verified at `agents.py:302` and `monitoring.py:120-124` on 2026-08-01: the kwarg is typed as the `LogLevel` `IntEnum`, with named values `OFF` (-1), `ERROR` (0), `INFO` (1), and `DEBUG` (2). Pass the named value rather than the raw integer; the names survive future renumbering.

## Capture per-step events

`step_callbacks` is the observation hook. Pass a list or a step-type-keyed dictionary whose values are small callables; each callable receives a typed memory-step object plus the agent itself. Use the dictionary form to scope a callback to `ActionStep`, `PlanningStep`, or `FinalAnswerStep` separately. The callback fires after `_finalize_step` has stamped the step's `end_time`, so per-step timing is available.

```python
from smolagents import ActionStep, ChatMessage, CodeAgent, Model


class Stub(Model):
    def generate(self, messages, **kwargs):
        return ChatMessage(
            role="assistant",
            content='<code>final_answer("done")</code>',
        )


durations = []


def record_duration(step, agent):
    if isinstance(step, ActionStep) and step.timing.duration:
        durations.append(step.timing.duration)


agent = CodeAgent(
    tools=[],
    model=Stub(),
    step_callbacks={ActionStep: record_duration},
    max_steps=1,
)
agent.run("Return done.")
print(durations)
assert durations  # at least one duration captured
```

Each callback receives the typed step as its first argument. The second argument is the agent itself when the callable's signature accepts it; legacy single-argument callbacks still work because the dispatch inspects the signature. Treat the callback as observation, not control: a mutation on the stored step does not steer the next prompt, because the prompt is rebuilt from the original step objects by `write_memory_to_messages()`.

## Gate the candidate answer

`final_answer_checks` is the framework's "do not let a bad answer escape" gate. Each callable receives the candidate answer, the agent's memory, and the agent itself, and returns a truthy value to accept or a falsy value to reject. The framework runs every check in order after the model emits its terminator call; a rejection becomes `AgentError` with the failing check's name preserved. The check cannot rewrite the candidate.

Verified at `agents.py:613-623` on 2026-08-01: the dispatch uses an `assert`, so any truthy value passes and the validator runs once per `.run()` call. Idiomatic beginner shapes are a length cap, a content keyword check, and a structural JSON check. `final_answer_checks` is end-of-run; `step_callbacks` is per-step.

## Use the AgentLogger and Monitor

The `AgentLogger` class is the surface that prints coloured console output, gated by the verbosity level you set on the agent. Its most useful entry points are `log_markdown`, `log_code`, `log_rule`, `log_messages`, and `log_task`. The `Monitor` class tracks totals: it appends each step's duration to `step_durations` and accumulates input and output token counts, exposed through `get_total_token_counts()`.

Verified at `monitoring.py:130-273` and `monitoring.py:81-118` on 2026-08-01: the default console is `rich.console.Console(file=None)`, which writes to standard output, not standard error. Beginners who want logs on stderr should pass a custom `Console(file=sys.stderr)` to `AgentLogger(level=..., console=my_console)` rather than reaching for a handler rewrite.

## Read RunResult after the run

When the agent finishes, `.run()` can return either the bare final answer (the default) or a richer `RunResult` object when `return_full_result=True`. The `RunResult` carries five fields: `output` (the answer), `state`, `steps`, `token_usage`, and `timing`.

The `state` field is the literal string `"success"` for a normal finish or `"max_steps_error"` when the agent ran out of step budget. The `steps` list is the durable record, one plain dictionary per memory step in the order they happened. The `timing` field is a `Timing` dataclass with `start_time`, `end_time`, and a read-only `duration` property.

```python
from smolagents import ActionStep, ChatMessage, CodeAgent, Model


class Stub(Model):
    def generate(self, messages, **kwargs):
        return ChatMessage(
            role="assistant",
            content='<code>final_answer("result: 42")</code>',
        )


agent = CodeAgent(
    tools=[],
    model=Stub(),
    max_steps=1,
    return_full_result=True,
)
result = agent.run("Return the result.")

assert result.output == "result: 42"
assert result.state == "success"
assert len(agent.memory.steps) == 2
assert isinstance(agent.memory.steps[0].task, str)
assert isinstance(agent.memory.steps[1], ActionStep)
assert agent.memory.steps[1].timing.duration > 0

print(result.output, result.state, agent.memory.steps[-1].timing.duration)
```

The `steps` list is `list[dict]`, not `list[ActionStep]` — index by key (`step_dict["step_number"]`) rather than by attribute. A deprecated `messages` alias still exists on `RunResult` but emits `FutureWarning`; the chapter does not use it.

## Walk the typed step journal

After `.run()` returns, `agent.memory.steps` is the agent's running journal — a list of typed step objects in the order they happened. There are three kinds: `TaskStep` (the user request that started the run), `ActionStep` (one per agent step), and `PlanningStep` (one per re-plan step when `planning_interval` is set).

The final-answer step is not appended to the list; it surfaces as `RunResult.output`. Beginners read the journal with `isinstance(step, ActionStep)` to pull the per-step data they care about. Verified at `memory.py:230` and `agents.py:611` on 2026-08-01: the `AgentMemory.steps` type annotation explicitly omits `FinalAnswerStep`, so the chapter reads the answer from `RunResult.output` rather than the journal's tail.

## Find slow steps via timing

Every step records when it started and when it ended; the difference lives at `step.timing.duration`, a property of the nested `Timing` dataclass. The value is `None` while the step is still in progress and a float in seconds after `_finalize_step` runs.

Beginners spot outliers by filtering for `ActionStep` instances and sorting by `duration`. The aggregate counterpart, `agent.monitor.step_durations`, holds one float per step and feeds average and total elapsed time.

The duration is wall-clock time (`time.time()` at `agents.py:622`), so it is an estimate, not a benchmark. Use it to find slow steps, not to enforce hard deadlines. A budget rule of thumb is `predicted_seconds = max_steps * expected_seconds_per_step`; a run that takes noticeably more than that is looping or stalled on a tool.

## Triage the six error classes

When a run fails, smolagents raises one of six named exception classes, all rooted at `AgentError`. `AgentMaxStepsError` means the step budget ran out; raise `max_steps` or split the task. `AgentParsingError` means the model emitted something the framework could not parse; the next iteration usually retries because the framework feeds the error back into the step.

`AgentToolExecutionError` means a tool was called correctly but failed at runtime; catch it and inspect the tool. `AgentGenerationError` wraps any failure during the model's generation step — provider connection drop, malformed response, parsing failure of the model's output. The framework is correctly bubbling the error up; the cause is usually provider-side (network, auth, model down) or response-shape, not a bug in smolagents itself.

`AgentError` is also raised by `final_answer_checks` rejections, so a broad catch at the workflow boundary catches both validator and run-time failures.

Verified at `utils.py:95-138` on 2026-08-01: `AgentToolExecutionError` and `AgentToolCallError` both subclass `AgentExecutionError`; beginners should treat the lumped form as one failure mode — the tool or its arguments were wrong. The triage table is `AgentMaxStepsError` → raise budget; `AgentParsingError` → usually no action; `AgentToolExecutionError` → catch and inspect; `AgentGenerationError` → fix the code; bare `AgentError` from a check → relax the gate.

## Run a small gold-answer evaluator

A pragmatic evaluator is a list of `(task, expected_answer)` tuples plus a loop that runs each case with `return_full_result=True` and records the verdict. The pattern needs no new framework; it is plain Python over `RunResult`.

A case passes only when both `state == "success"` AND `output == expected`. A `state == "max_steps_error"` case is a failure regardless of what `output` happens to contain. For open-ended answers, swap the equality check for a deputy judge call to another agent whose prompt embeds the criteria.

ch-14 — Test Agents Without Guessing — promotes this loop into a pytest function so the records list becomes a test report. ch-15 — Keep Agents Safe and Responsible — sets the guardrails you'd want before running this loop against a live provider.

Here is the loop end to end with three cases.

```python
from smolagents import ChatMessage, CodeAgent, Model

CASES = [
    ("What is 2+2?", "4"),
    ("Capital of France?", "Paris"),
    ("Reverse 'hello'?", "olleh"),
]
BY_TASK = {task: ans for task, ans in CASES}


class Stub(Model):
    def generate(self, messages, **kwargs):
        for m in messages:
            text = m.content[0]["text"] if isinstance(m.content, list) else str(m.content)
            if text.startswith("New task:"):
                text = text.split("New task:", 1)[1].lstrip()
                break
        return ChatMessage(
            role="assistant",
            content=f'<code>final_answer("{BY_TASK[text]}")</code>',
        )


results = []
for task, expected in CASES:
    result = CodeAgent(tools=[], model=Stub(), max_steps=1).run(task, return_full_result=True)
    passed = result.state == "success" and result.output == expected
    results.append((task, expected, result.output, result.state, result.token_usage, passed))

assert all(r[5] for r in results), "some cases failed"
print(f"PASS 3/3 cases; last output={results[-1][2]!r} state={results[-1][3]!r}")
```

```text
PASS 3/3 cases; last output='olleh' state='success'
```

## Avoid four beginner errors

**Reading memory before `.run()` completes.** The list starts empty after construction and stays empty until the first call appends a `TaskStep` at `agents.py:488`. Inspect `agent.memory.steps` only after `.run()` returns; otherwise the list is `[]` and the agent looks broken.

**Drowning in `LogLevel.DEBUG` output.** Pick `LogLevel.INFO` for the happy path and switch to `DEBUG` only when a single bad run needs a closer look. Reconstruct the agent with a new `logger=` for each verbosity tier rather than scrolling past thousands of lines.

**Mutating memory to rewrite history.** `step_callbacks` is for observing. A mutation on a stored step does not influence the next prompt because the prompt is rebuilt from the original step objects. Treat `agent.memory` as observability, not control.

**Silencing `AgentError` with a bare `except`.** The exception classes are intentionally informative. Catch the specific subclass, log the message, and re-raise if you cannot fix it. A silent `except` discards both the message and the stack trace.
