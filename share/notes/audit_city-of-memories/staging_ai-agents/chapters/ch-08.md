# Chapter 8 — How Agents Work: A Toy Agent from Scratch

When you run the ch-07 conversation script, the model answers once and the terminal waits. Imagine the answer naming a lookup operation instead: your program must read that name, call the matching Python function, show the result to the model, and ask again. This chapter builds that small loop before a framework hides the moving parts.

## Trace the four-step cycle

An agent loop is a four-step cycle: **observe → decide → act → observe**. You read the current task or the last result, ask the model what to do, call the selected tool, and read what came back. Then you repeat the cycle. The model is one input to the program; the loop controls the run.

The ReAct paper by Yao and colleagues names this interleaving as Thought, Action, and Observation. Anthropic's *Building effective agents* gives the same practical distinction: an agent lets the model dynamically direct the next step, while a workflow fixes the route in advance. Here, the route is visible Python control flow.

The first **observe** reads the user's task and the running message history. **Decide** sends that state to the model and receives a proposed action. **Act** looks up a Python function and calls it. The second **observe** records the function's return value. Those four moves are the agent; the model supplies one decision inside them.

## Set the prompt contract

The prompt is a contract between your program and the model. Give it four ingredients in a stable order so the next action has a predictable shape.

- **Goal:** put the user's task in a user message, as a plain string.
- **Available tools:** list each tool name, its parameter names and types, and what it returns.
- **Action grammar:** show one valid JSON action and one `done` action as worked examples.
- **History:** send every earlier assistant action and every tool observation in order.

Put standing rules in the system message and the task in the user message. The system message in the example below says which tool exists and shows the exact JSON keys. The user message carries the goal. After the first turn, the message list carries the history, so the model can see what it chose and what the tool returned.

A missing ingredient creates a recognizable failure. Without the tool list, the model can invent a name. Without the action grammar, it can answer in paragraphs instead of JSON. Without history, it can repeat the first choice because it cannot see the observation that should change its decision. The prompt contract lets you predict the failure before you run the code.

## Parse the model's action

A model returns text. Your loop must turn that text into a tool name and an argument dictionary before Python can call anything. This is **action parsing**: the boundary between a string such as `{"action": "lookup", "action_input": {"term": "python"}}` and a Python dictionary with the same fields.

The example uses `json.loads`, documented in Python's standard-library `json` module. A second toy pattern uses `re.search` to read a grammar such as `Action: lookup / Input: python`. Both approaches make the boundary visible. The code chooses JSON because the action name and arguments stay together and the parser remains short.

Production APIs offer server-enforced JSON modes and native tool-call messages. This chapter keeps raw text on purpose so you can see the parse step, the parse failure, and the recovery message rather than treating structured output as an invisible service.

## Dispatch through a dictionary

After parsing, the loop uses a Python dictionary as a dispatch table: a mapping from the model's chosen name to a callable function. `tools.get(name)` returns the function when the name matches. The loop then calls it with `tool(**action_input)`, so the JSON keys become Python keyword arguments.

The Python standard-library documentation for `dict`, `try`, and exceptions gives you the pieces needed here. Check for a missing name before calling. Catch a wrong argument list and catch an exception raised inside the tool. Turn each failure into a string in the history. The next model turn can read that observation and choose a correction.

## Wrap the ch-07 request

Chapter 7 made one model call and printed its reply. This chapter makes one call, reads the proposed action, runs a tool, and makes another call. The `requests.post` body, bearer header, explicit timeout, `load_dotenv()`, and `load_api_key()` pattern are the same. The new part is the loop between two requests.

Conceptually, the ch-07 request now sits inside `while True`. A counter checked at the top supplies the second exit, so the loop cannot run forever when the model keeps choosing tools. The core loop below is the roughly thirty-line move; its surrounding request helper is the ch-07 pattern you already know.

```python
import json
import os

import requests
from dotenv import load_dotenv

CHAT_URL = "https://api.openai.com/v1/chat/completions"
SYSTEM_PROMPT = (
    "Use lookup(term: str) when needed. Return JSON only: "
    '{"action":"lookup","action_input":{"term":"python"}} or '
    '{"action":"done","action_input":{"answer":"..."}}.'
)


def load_api_key(name: str) -> str:
    load_dotenv()
    key = os.getenv(name)
    if not key:
        raise SystemExit(f"Set {name} in .env or your shell.")
    return key


def ask_model(messages: list[dict], api_key: str) -> str:
    response = requests.post(
        os.getenv("OPENAI_CHAT_URL", CHAT_URL),
        json={
            "model": os.getenv("OPENAI_MODEL", "your-model-id"),
            "messages": messages,
        },
        headers={"Authorization": f"Bearer {api_key}"},
        timeout=30,
    )
    response.raise_for_status()
    return response.json()["choices"][0]["message"]["content"]


def lookup(term: str) -> str:
    facts = {
        "python": "Python is a programming language.",
        "agent": "An agent is a program with a model-driven loop.",
    }
    return facts.get(term.lower(), f"No note for {term}.")


def run_agent(task: str, api_key: str, max_steps: int = 8) -> str:
    messages = [
        {"role": "system", "content": SYSTEM_PROMPT},
        {"role": "user", "content": task},
    ]
    tools = {"lookup": lookup}
    step = 0
    while True:
        if step >= max_steps:
            raise RuntimeError(f"Stopped after {max_steps} steps.")
        step += 1
        reply = ask_model(messages, api_key)
        messages.append({"role": "assistant", "content": reply})
        try:
            action = json.loads(reply)
        except json.JSONDecodeError as exc:
            messages.append(
                {
                    "role": "user",
                    "content": f"Use the JSON action format: {exc}",
                }
            )
            continue
        name = action.get("action")
        if name == "done":
            return action["action_input"]["answer"]
        tool = tools.get(name)
        if tool is None:
            result = f"Unknown tool {name}; choose lookup or done."
        else:
            try:
                result = tool(**action.get("action_input", {}))
            except Exception as exc:
                result = f"Tool error: {type(exc).__name__}: {exc}"
        messages.append(
            {"role": "user", "content": f"Observation from {name}: {result}"}
        )


if __name__ == "__main__":
    key = load_api_key("OPENAI_API_KEY")
    print(run_agent("Define Python in one sentence.", key))
```

Read the loop from top to bottom. `messages` starts with the contract and the goal. `ask_model` is the decide step. The assistant reply is appended before parsing, preserving the record of what the model chose. `json.loads` creates the action dictionary. The dictionary lookup is the act step. Finally, the tool's text is appended as a new observation for the next request.

The toy records an observation with a user-role message because it uses a text-only protocol. A provider's native tool protocol uses an assistant action followed by a tool message with matching metadata. The invariant is the same: record the chosen action first, then record the result, in that order. The history grows by one turn per step and consumes the model's context window.

## Stop with two guards

The first guard is the model's `done` action. When the parser sees `"action": "done"`, the loop returns the answer instead of dispatching a function. Treat that signal as data your program checks, not as a sentence you infer from the model's tone. A structured stop is easier to test than searching for phrases such as “that is all.”

The second guard is `max_steps=8`. It caps requests and keeps the message history from growing without bound. A task that needs more steps should fail with a visible `RuntimeError` and a limit you can inspect. Anthropic's *Building effective agents* emphasizes explicit stop conditions for agentic runs; the Python standard-library `while` and `for` documentation gives you the control-flow tools to enforce one.

## Replace the model with a stub

You can test the loop without a provider account. An offline stub is a plain function that accepts the current `messages` list and returns canned model replies. The rest of the program does not know that the model was replaced: it still parses the reply, dispatches `lookup`, appends the observation, and asks for the next reply.

The stub below returns one tool action and then a `done` action. It prints each model reply and tool result, so the observe–decide–act–observe cycle appears as a deterministic trace. The `assert` turns the example into a runnable check that fails loudly if the loop returns the wrong answer.

```python
import json


def lookup(term: str) -> str:
    facts = {"python": "Python is a programming language."}
    return facts.get(term.lower(), f"No note for {term}.")


def run_agent(task: str, model_reply, max_steps: int = 8) -> str:
    messages = [
        {
            "role": "system",
            "content": "Use lookup(term: str), then return JSON.",
        },
        {"role": "user", "content": task},
    ]
    tools = {"lookup": lookup}
    for step in range(1, max_steps + 1):
        reply = model_reply(messages)
        print(f"step {step}: model -> {reply}")
        messages.append({"role": "assistant", "content": reply})
        action = json.loads(reply)
        if action["action"] == "done":
            answer = action["action_input"]["answer"]
            print(f"done: {answer}")
            return answer
        name = action["action"]
        tool = tools.get(name)
        if tool is None:
            result = f"Unknown tool {name}"
        else:
            try:
                result = tool(**action.get("action_input", {}))
            except Exception as exc:
                result = f"Tool error: {type(exc).__name__}: {exc}"
        print(f"tool result: {result}")
        messages.append({"role": "user", "content": f"Observation: {result}"})
    raise RuntimeError(f"Stopped after {max_steps} steps.")


def make_stub_model():
    replies = iter(
        [
            '{"action": "lookup", "action_input": {"term": "python"}}',
            '{"action": "done", "action_input": '
            '{"answer": "Python is a programming language."}}',
        ]
    )

    def stub_model(messages):
        return next(replies)

    return stub_model


if __name__ == "__main__":
    answer = run_agent("What is Python?", make_stub_model())
    assert answer == "Python is a programming language."
```

Run the stub in the chapter's virtual environment. It produces two model steps, one tool-result line, and `done: Python is a programming language.` No network call occurs. Because the stub receives `messages`, you can later make its next reply depend on the observation instead of returning a fixed sequence. That same replacement pattern becomes useful when you test larger agents.

## Name the DIY costs

The hand-written loop has two specific costs. First, it has **no parallel tool calls**. If one model reply names three independent lookups, this parser reads one action, runs one function, and pays for another model request before it can see the next action. The program cannot dispatch the three functions together because its action grammar has room for one choice.

Second, it has **no schema-aware retries**. If the model returns almost-valid JSON, `json.loads` reports a parse error and the loop sends that error back on the next model turn. That malformed response costs a full round trip. A framework can validate the shape locally and retry or repair a step before asking the provider again.

Per Anthropic's *Building effective agents* (the same source cited above for the ReAct framing), parallel tool dispatch and structured-output validation are two of the things a framework can automate.

Those costs are part of the lesson, not a hidden defect. You can see exactly what a framework will need to automate: prompt assembly, action parsing, name-to-tool dispatch, step control, and the structured stop signal. The next chapter adds typed schemas, retryable step errors, and tool errors that carry agent context.

## Fix four beginner errors

These four failures appear before any advanced agent feature. Name the traceback category, then apply the smallest fix that keeps the model informed.

1. **Infinite loop without a `max_steps` guard.** The model keeps returning a tool action, so the process runs until you stop it. Traceback category: none until manual interruption. Fix: check `if step >= max_steps` before each model call.

2. **The model returns prose instead of a structured action.** `json.loads` raises `json.JSONDecodeError`; valid but incomplete JSON can raise `KeyError`. Fix: catch the parser error and append “Use the documented JSON action format” to the history before the next call.

3. **The action name does not match a tool.** A missing dictionary entry can become `TypeError: 'NoneType' object is not callable` when the result is called without a check. Fix: test the dictionary lookup and report the available names in the next observation.

4. **A tool exception goes unwitnessed.** A bad argument or a failing function raises `TypeError`, `ValueError`, or another exception and kills the run. Fix: catch `Exception`, convert the error to a short observation, and let the model choose a different action.

## Keep the loop as a lesson

This toy agent is for understanding the loop, not for adopting a hand-rolled agent in production. It has no provider-native schema enforcement, parallel dispatch, retry policy, permission boundary, or durable trace. Those omissions keep the moving parts exposed. In a real application, add the controls your tools and data require before model output can cause side effects.
