At the prompt, you run `E:\book_gen\.venv\Scripts\python.exe -m pytest tests/test_agent.py -v`. Three cases pass, then the next run waits on a provider timeout. The terminal has told you two different stories because the test included a live model. This chapter replaces that uncertainty with a deterministic stub and assertions over the agent's real run record.

## Make Tests Deterministic

A normal function maps inputs to outputs inside one process. An agent adds a model call, a prompt, a network boundary, and often a side effect. Sampling can vary; prompt wording can change behavior; a provider can change its model; a timeout, rate limit, or server error can interrupt the run. The same task can therefore produce different output or different timing without any change to your Python.

Don't try to make the entire agent deterministic. Make the slice under test deterministic. Replace the provider model with a stub that returns a known `ChatMessage`, then let the real agent build prompts, parse code, dispatch tools, record steps, and package the result. The stub removes model randomness and network flakiness while leaving your application path in place.

This boundary tells you what the test can and cannot prove. It catches broken wiring, parser assumptions, callback registration, and result handling. It doesn't tell you whether a live model follows a changed prompt. Keep that question for a separate evaluation or integration suite. The installed 1.26.0 runtime calls the model from `MultiStepAgent` during each step, so this split follows the real execution boundary (`agents.py:436-611`).

## Stub the Model

In 1.26.0, subclass `Model` and override `generate`. Don't override `__call__` as the test seam. `Model.__call__` is a convenience wrapper, while the runtime invokes `self.model.generate(...)` directly at `agents.py:1309`. A stub that changes only the wrapper still falls through to the base `generate` method and raises `NotImplementedError`.

Your `generate` method receives the message list and returns a `ChatMessage`. For a `CodeAgent`, return a code blob containing the framework's answer tool call. For a multi-step test, keep a call counter and return a different blob on each call. This chapter's suite dispatches on the task text, which gives each gold case a stable answer without a provider credential.

Call `super().__init__()` so the base `Model` initializes its ordinary fields (verified at `models.py:484` in the installed smolagents==1.26.0 source, 2026-08-01). You don't need a provider client, token, or model identifier in a test double. That keeps the fixture local and makes a failing test point toward your agent plumbing rather than an authentication setup.

## Cap Each Run

`max_steps=1` is a useful default for a unit test that needs one model response and one action. It bounds the loop, keeps the test quick, and makes its scope visible in the constructor. Pass it again to `.run(...)` when you want the limit visible at the assertion site; the per-call value takes precedence (`agents.py:443-468`).

Use a larger budget only when the test is about recovery or a multi-step route. A test that needs three actions should say `max_steps=3`; a test that checks one answer should not inherit a broad loop budget. This distinction prevents a regression from hiding inside extra retries.

When a run exhausts its budget, smolagents 1.26.0 records `AgentMaxStepsError` on the last action step. With `return_full_result=True`, the public result reports `state == "max_steps_error"` rather than requiring that condition to escape the call (`agents.py:523-536, 625`). Test the public state first.

## Record Agent Steps

Attach `step_callbacks` when the assertion is about what the agent did. The dictionary form, `{ActionStep: record_step}`, limits the hook to action steps. Your callback receives the typed step and the agent; append the step to a list, then inspect it after `.run()` returns. The callback is dispatched synchronously during step finalization (`memory.py:280-316`).

An action record can tell you that the model emitted a completion call, selected a tool, or produced an observation. That is more reliable than searching console text because the callback sees the framework's parsed step object. Keep the callback observational. It records evidence; it should not mutate the run to force a different branch.

## Capture Logger Output

Logs are a second assertion surface. Subclass `AgentLogger`, override `log`, and store the arguments in a list. Pass the instance with `logger=`. Don't pass `monitor=`: `MultiStepAgent.__init__` accepts `logger=`, while it constructs its internal `Monitor` after initialization. This kwarg distinction was checked with `inspect.signature(...)` in the installed source.

Set the logger level to `LogLevel.OFF` in a test unless the test itself checks visible output. Your subclass can still record calls while keeping pytest's terminal report readable (per `AgentLogger.log` at `monitoring.py:138-146` in the installed smolagents==1.26.0 source, 2026-08-01). Assert that the record list is nonempty or inspect selected messages; avoid matching timestamps, colored markup, or provider-specific wording.

## Build Fresh Fixtures

`pytest.fixture` gives each test a fresh object graph. A function-scoped fixture is the safe default here. It rebuilds the stub, the agent memory, the callback list, and the logger for every case.

Shared mutable memory can make a later test pass because an earlier test left a task or step behind. Keep the fixture in the same test file while the suite is small; move it to `conftest.py` when several modules need the same setup.

## Parameterize Gold Cases

`pytest.mark.parametrize` owns the loop that ch-13 wrote by hand. Store `(task, expected_answer)` tuples, pass them to the decorator, and give the cases readable `ids`. Pytest then reports one result per case while the test body stays single. This is the gold-answer pattern: compare the agent's returned output, not the model's raw message.

The following file uses `CodeAgent(tools=[], model=StubModel(), max_steps=1)`, a task-dispatching `generate`, a callback, a logger subclass, a fixture, three parametrized gold cases, and one bounded failure case.

```python
import pytest
from smolagents import (
    ActionStep, AgentLogger, AgentMaxStepsError, ChatMessage, CodeAgent,
    LogLevel, Model,
)

CASES = [("add two numbers", "4"), ("reverse a word", "tac"),
         ("name a color", "blue")]
ANSWERS = dict(CASES)


class StubModel(Model):
    finish = True

    def generate(self, messages, **kwargs):
        if not self.finish:
            code = "print('waiting')"
        else:
            task = messages[-1].content[0]["text"].split("New task:\n")[1]
            code = f"final_answer({ANSWERS[task]!r})"
        return ChatMessage(role="assistant", content=f"<code>{code}</code>")


class CapturingLogger(AgentLogger):
    def log(self, *args, **kwargs):
        self.records = getattr(self, "records", [])
        self.records.append((args, kwargs))


def record_step(step, agent):
    agent.test_steps.append(step)


@pytest.fixture
def agent():
    instance = CodeAgent(
        tools=[], model=StubModel(), max_steps=1,
        step_callbacks={ActionStep: record_step},
        logger=CapturingLogger(level=LogLevel.OFF),
    )
    instance.test_steps = []
    return instance


@pytest.mark.parametrize(
    ("task", "expected"), CASES, ids=["add", "reverse", "color"]
)
def test_gold_answer(task, expected, agent):
    result = agent.run(task, max_steps=1, return_full_result=True)

    assert result.output == expected
    assert result.state == "success"
    assert agent.test_steps[0].is_final_answer
    assert agent.logger.records


def test_failure_records_max_steps(agent):
    agent.model.finish = False
    result = agent.run("never finish", max_steps=1, return_full_result=True)

    assert result.state == "max_steps_error"
    with pytest.raises(AgentMaxStepsError):
        raise agent.memory.steps[-1].error
```

## Inspect Failure States

Run it as `E:\book_gen\.venv\Scripts\python.exe -m pytest test_agent.py -v`. The happy cases assert `result.output` and `result.state`; they also assert the callback saw the completed action and the logger captured calls. The failure case checks the public state, then uses `pytest.raises(AgentMaxStepsError)` on the recorded error object. That pair makes the test match both the run envelope and the exception type.

That second assertion is deliberate. In this runtime, the max-step handler stores the exception and returns a fallback answer so the full result can describe the failure. `pytest.raises` remains the right tool when your own code or a helper is expected to raise; here it verifies the stored exception class without pretending the agent call itself must throw.

`return_full_result=True` changes the return value from a bare answer to `RunResult`. Assert `output` for caller-visible content and `state` for completion status. Use `result.steps` when you need the serialized transcript; it is a list of dictionaries. The callback list contains typed memory steps, so the two surfaces complement each other rather than duplicate each other (`agents.py:196-253`).

Don't make timing or token totals part of a gold-answer assertion. `RunResult.timing` uses wall-clock measurements, and provider token counts vary with prompts and backend behavior. Those fields are useful for a performance or cost test with a stated tolerance, not for the correctness test that should run on every commit.

## Keep Async Tests Synchronous

`MultiStepAgent.run` is synchronous in smolagents 1.26.0; `inspect.iscoroutinefunction(...)` returns `False`. Write these agent tests with ordinary `def` functions. `pytest-asyncio==1.4.0` is useful when a custom tool performs asynchronous work, but the plugin doesn't turn a synchronous agent run into an async operation.

For an async test, use `@pytest.mark.asyncio` in strict mode, or set `asyncio_mode = "auto"` in pytest configuration. Pick one deliberate mode. Don't mark a synchronous `.run()` test as async, and don't create a global async setting for a suite that contains no async tests.

## Avoid Four Beginner Errors

Assert on the agent's output rather than the raw model message. The model's `ChatMessage` is an input to the agent, not a value your caller sees; use `result.output` for the answer your code returns.

Set an explicit step cap. A test that doesn't need the inner loop should state `max_steps=1` so the run stays small and a regression cannot hide inside extra retries.

Reserve timing and token assertions for dedicated tests. Those quantities vary across machines and providers, so they flake in a unit suite that should run on every commit.

Configure async mode only when the suite contains async tests. The plugin is a knob for tools that perform async work, not background noise for a synchronous agent run.

## Scale the Pattern

Keep the stub suite as the fast layer. Add a live layer only when you need to observe prompt sensitivity, provider changes, network behavior, or real tool side effects. Mark that layer separately and give it its own failure policy; mixing it into the unit run turns a local regression into an intermittent terminal report.

At project scale, ch-17 — Choose and Operate Model Backends — can run the same gold cases against each configured backend adapter. The expected strings stay small, while backend selection and credential boundaries become the integration surface. The stub remains the first check because it isolates routing and result handling.
