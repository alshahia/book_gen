# Chapter 12 — Create Structured Agent Workflows

The terminal shows a draft, then waits: should the manager accept it, ask a specialist, or run another pass? You can build that decision in ordinary Python. This chapter keeps one top-level agent in charge, adds a named specialist, observes completed steps, gates accepted answers, and loops with bounded retries.

## Name the workflow shapes

A workflow is a developer-shaped route through model calls and tools. You choose the route in Python, while the agent chooses actions inside its bounded run. This chapter stays with one manager agent and its managed specialist. Chapter 16 handles coordination among several top-level agents.

Anthropic's *Building effective agents* names five useful patterns. Prompt chaining sends one call's output into the next. Parallelization runs independent tasks or repeated votes. Routing classifies input and sends it to a specialist. Orchestrator-workers lets a central model delegate dynamically. Evaluator-optimizer alternates a draft with critique and revision.

You can express chaining and evaluator-optimizer with ordinary `.run()` calls. The other shapes still matter, but they introduce coordination decisions that deserve their own treatment. The important boundary is visible: Python owns the outer route, and the agent owns its inner step loop.

## Delegate to a specialist

Pass `managed_agents=[specialist]` to `CodeAgent` or `ToolCallingAgent` when the manager should call a named specialist. In smolagents 1.26.0, `MultiStepAgent.__init__` registers each child alongside ordinary tools. The child needs a non-empty `name` and `description`, and its name must be a valid Python identifier.

The manager calls the specialist with a `task` string and optional `additional_args`. The specialist runs its own loop and returns a string-shaped report. The two agents keep separate memory, so inspect the child directly when its steps matter. This is composition inside one workflow, not yet a team of independent managers.

The handoff templates use inner keys: `{{name}}`, `{{task}}`, and the final-answer template key. They are not nested paths. The first pair describes the managed task; the final-answer key wraps the specialist's report. This detail is verified against the installed 1.26.0 source and prevents a template lookup that cannot render.

```python
import os

from smolagents import ToolCallingAgent, InferenceClientModel, tool

MODEL_ID = os.getenv(
    "HF_AGENT_MODEL",
    "Qwen/Qwen2.5-Coder-7B-Instruct",
)


@tool
def add_numbers(left: int, right: int) -> int:
    """Add two integers.

    Args:
        left: The first integer.
        right: The second integer.
    """
    return left + right


model = InferenceClientModel(model_id=MODEL_ID)
specialist = ToolCallingAgent(
    tools=[add_numbers],
    model=model,
    name="calculator_specialist",
    description="Calculates integer sums for the manager.",
    max_steps=8,
)
manager = ToolCallingAgent(
    tools=[],
    model=model,
    name="workflow_manager",
    description="Routes calculation tasks to a specialist.",
    managed_agents=[specialist],
    max_steps=8,
)

# result = manager.run("Ask the calculator specialist for 19 + 23.")
# print(result)
```

The example is provider-ready but does not call the network while parsed as a file. You can replace the commented run with a real call after setting the provider credential. If the manager has several ordinary functions and the specialist should look like one more function, wrap `specialist.run(task)` in a typed `@tool` instead. Use `managed_agents` when the named-agent identity and managed report belong in the prompt.

## Observe completed steps

`step_callbacks` receives completed steps before and after model and tool execution has been finalized. The constructor accepts a list or a type-keyed dictionary. A list is the compatibility form for action steps. A dictionary can register callbacks for `ActionStep`, `PlanningStep`, or `FinalAnswerStep` separately.

Start with one callback that records a compact event. The callback may accept `step` alone, or `step` and `agent`; smolagents 1.26.0 supports both signatures. Treat it as an observation hook. Record facts for later inspection rather than trying to rewrite the agent's next decision from inside the callback.

```python
from smolagents import ActionStep, CodeAgent, Model, ChatMessage


class StubModel(Model):
    def generate(self, messages, **kwargs):
        return ChatMessage(
            role="assistant",
            content='<code>final_answer("logged")</code>',
        )


captured = []


def record_step(step, agent):
    captured.append(type(step).__name__)


agent = CodeAgent(
    tools=[],
    model=StubModel(),
    step_callbacks=[record_step],
    max_steps=1,
)
assert agent.run("Return a logged value.") == "logged"
assert captured == ["ActionStep"]
print(captured)
```

The callback runs after the step has been finalized, and the agent retains its own memory. A callback mutation is not a reliable way to steer the next prompt. If the next call needs new context, pass `additional_args` explicitly. That makes the data flow visible in the Python code.

## Gate the accepted answer

Use `final_answer_checks` for predicates that decide whether a candidate is acceptable. Each callable receives the candidate, the agent memory, and the agent itself. A truthy result accepts it. A falsey result, or an exception raised by the predicate, becomes `AgentError` and blocks the return.

A predicate cannot rewrite the candidate. It can only accept or reject. Keep each check small, name the rule, and catch `AgentError` at the workflow boundary when you want to retry with better instructions.

```python
from smolagents import AgentError, ChatMessage, CodeAgent, Model


class AnswerModel(Model):
    def generate(self, messages, **kwargs):
        return ChatMessage(
            role="assistant",
            content='<code>final_answer("result: 42")</code>',
        )


def is_short(answer, memory, agent):
    return len(str(answer)) <= 32


def contains_result(answer, memory, agent):
    return "result" in str(answer).lower()


agent = CodeAgent(
    tools=[],
    model=AnswerModel(),
    final_answer_checks=[is_short, contains_result],
    max_steps=1,
)
answer = agent.run("Return a short result.")
assert answer == "result: 42"
print(answer)
```

The two checks demonstrate different gates. `is_short` enforces shape; `contains_result` enforces content. If the model returns a long answer, the first check rejects it. If it returns a short answer without the required word, the second rejects it. The framework raises `AgentError`, so your outer loop can decide whether to retry, report failure, or change the task.

## Budget each agent

`max_steps` belongs to one agent's run. A manager's budget does not cascade to managed children. If both have a budget of eight, the child can use eight and the manager can use eight more. Set budgets per role, according to the work that role must complete.

`planning_interval` also belongs to one agent. It inserts periodic planning steps into that agent's loop; it does not configure its managed children. Short specialist tasks can leave it as `None`. Longer tasks can use a positive interval, while remembering that each planning call adds model work and context.

A low budget is a workflow bug when a full iteration cannot produce, check, and revise a candidate. Catch `AgentMaxStepsError`, then raise the relevant agent's budget or split the task. Do not let an outer retry loop hide a per-run cap that is too small.

## Chain outputs in Python

There is no required workflow helper for a sequential chain. Call the first agent, keep its result, then pass that result to the second agent. `reset=False` preserves the second agent's earlier context when you make a follow-up call; `additional_args` makes the first result available as named state as well.

This example shows two sequential calls. The second task uses the first result, and both calls are explicit enough to insert a condition later.

```python
from smolagents import ChatMessage, CodeAgent, Model


class ChainModel(Model):
    def __init__(self):
        super().__init__()
        self.calls = 0

    def generate(self, messages, **kwargs):
        self.calls += 1
        body_text = " ".join(
            str(getattr(m, "content", "") or "") for m in messages
        )
        if self.calls == 1:
            body = "plan: check inputs"
        else:
            body = "executed" if "Plan:" in body_text else "plan: check inputs"
        return ChatMessage(
            role="assistant",
            content=f'<code>final_answer("{body}")</code>',
        )


agent = CodeAgent(tools=[], model=ChainModel(), max_steps=1)
task = "Prepare a small validation task."
plan = agent.run(task)
result = agent.run(
    f"Plan:\n{plan}\n\nExecute the plan for: {task}",
    reset=False,
    additional_args={"plan": plan},
)
assert plan == "plan: check inputs"
assert result == "executed"
print(result)
```

The chain's data boundary is the Python variable `plan`. If an agent returns a dictionary or another typed value, call `str(plan)` before placing it in a text prompt. Chaining is a good fit when the stages and handoff fields are known before the run starts.

## Loop with an evaluator

An evaluator-optimizer loop has a producer, a quality rule, and a bounded retry path. The producer returns a candidate. Python evaluates it. A passing candidate breaks the loop; a rejected candidate becomes a refinement instruction on the next call.

Use `reset=False` when the same agent should see its earlier attempt. Cap the loop with a `for` range or a counter. Each iteration adds context and token usage, so a loop that can continue forever is a cost and reliability problem.

```python
from smolagents import ChatMessage, CodeAgent, Model


class RefiningModel(Model):
    def __init__(self):
        super().__init__()
        self.calls = 0

    def generate(self, messages, **kwargs):
        self.calls += 1
        answer = "draft" if self.calls == 1 else "draft with source"
        return ChatMessage(
            role="assistant",
            content=f'<code>final_answer("{answer}")</code>',
        )


def meets_quality(answer):
    return "source" in str(answer)


model = RefiningModel()
agent = CodeAgent(tools=[], model=model, max_steps=1)
request = "Write a short note and include a source."
answer = ""

for attempt in range(3):
    answer = agent.run(request, reset=False)
    if meets_quality(answer):
        break
    request = (
        "Refine your previous draft. Include the word 'source' and return "
        "the complete note."
    )
else:
    raise RuntimeError("Quality threshold was not met.")

assert answer == "draft with source"
assert model.calls == 2
print(answer)
```

The stub model returns canned outputs, so the loop runs end to end without a provider. In production, replace the stub with your configured model and use a predicate that reflects the task. The outer loop is the evaluator; the agent run is the optimizer. The cap is part of correctness, not decoration.

## Catch the right failures

The installed 1.26.0 source exposes six named classes for this chapter's error map: `AgentError`, `AgentExecutionError`, `AgentToolExecutionError`, `AgentGenerationError`, `AgentParsingError`, and `AgentMaxStepsError`. `AgentExecutionError` is the parent for tool-related execution failures.

Catch `AgentMaxStepsError` when the per-agent budget was exhausted. Catch `AgentParsingError` when the model response could not become a structured action. Catch `AgentToolExecutionError` when a valid tool call failed at runtime. Catch `AgentGenerationError` as an implementation failure that needs code repair rather than blind retry.

Catch base `AgentError` for a failed validator or a user hook. A useful boundary catches the specific classes first, logs the task, then chooses retry or failure. The smolagents 1.26.0 source and its reference page are the authority for these names and inheritance relationships.

## Avoid four beginner errors

1. **Self-managing an agent.** Do not put the manager inside its own `managed_agents` list. The parent and specialist must be distinct objects, or recursive calls can exhaust Python's call stack.

2. **Assuming shared memory.** A managed child owns a separate memory object. Inspect `specialist.memory.steps` when you need its trace; the manager receives the child's report, not every intermediate step.

3. **Steering through callbacks.** A callback is for observing finalized steps. Mutating a step does not provide a dependable control channel. Pass new values through `additional_args` instead.

4. **Starving the loop.** A tiny `max_steps` can stop a produce-check-refine iteration before the quality rule runs. Give each participating agent enough budget, then bound the outer loop separately.

These errors all come from hiding a boundary: object ownership, memory ownership, callback timing, or retry ownership. Write those boundaries down in the workflow code before adding another branch.

## Make the workflow explicit

Name the manager, specialist, checks, callback, and loop counter. Keep each handoff as a Python value. That structure gives you places to log, test, and handle exceptions without asking the model to invent the whole program route.
