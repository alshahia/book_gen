# Chapter 17 — Choose and Operate Model Backends

A researcher points a draft agent at Hugging Face Inference while a writer selects `OpenAIModel` for a first-party OpenAI call. Both agents still receive a `model=` object, but the object hides different network, credential, hardware, and failure decisions. Your task is to make those decisions deliberate, then keep them in one small factory.

## Name the model contract

A model backend is the part of the agent that turns a prompt into a model response. The framework calls that boundary a model. In this chapter, application programming interface (API) means the network interface a hosted provider exposes; a local runtime performs the same contract without sending the prompt away.

In smolagents 1.26.0, `Model` is the abstract root class at `models.py:452`. Abstract means you inherit the contract or select a concrete child; you don't construct the root and expect it to know how to generate a response. `ApiModel` is the abstract API-backed subclass at `models.py:1138`. It supplies shared behavior for models that use a client to reach a remote service.

The API-backed children are `InferenceClientModel`, `OpenAIModel`, `AzureOpenAIModel`, `AmazonBedrockModel`, and `LiteLLMModel`. `LiteLLMRouterModel` also subclasses `ApiModel` through the LiteLLM path. The local-runtime children are `TransformersModel`, `VLLMModel`, and `MLXModel`; they extend `Model` directly because they don't own the HTTP client used by `ApiModel` (installed source, `models.py:633-1138`).

Think of the hierarchy as a routing map:

```python
from smolagents import ApiModel, Model

MODEL_SURFACE = (
    "Model",
    "ApiModel",
    "InferenceClientModel",
    "OpenAIModel",
    "AzureOpenAIModel",
    "AmazonBedrockModel",
    "LiteLLMModel",
    "LiteLLMRouterModel",
    "TransformersModel",
    "VLLMModel",
    "MLXModel",
    "OpenAIServerModel",
    "AmazonBedrockServerModel",
    "AzureOpenAIServerModel",
)


if __name__ == "__main__":
    print(len(MODEL_SURFACE))
    print(", ".join(MODEL_SURFACE))
```

The complete public surface has fourteen names. The two base names describe contracts, while the remaining names describe concrete provider or runtime choices. The three server variants are included in that surface, bringing the inventory to `OpenAIServerModel`, `AmazonBedrockServerModel`, and `AzureOpenAIServerModel`.

## Match provider to class

Choose `InferenceClientModel` for Hugging Face (HF) Inference API access. Give it a model identifier and, when needed, a token. If you leave the token argument out, smolagents reads `HF_TOKEN` and can also use a locally authenticated Hugging Face client (installed source, `models.py:1456-1645`). The package has its own default model, but you should set a small model explicitly so a beginner's first run doesn't inherit a heavyweight default.

Use an environment-backed identifier rather than putting a provider name in five files:

```python
import os

from smolagents import InferenceClientModel, OpenAIModel

OPENAI_MODEL_ID = os.getenv("OPENAI_MODEL", "small-openai-model")
HF_MODEL_ID = os.getenv("HF_MODEL", "small-hugging-face-model")


if __name__ == "__main__":
    print(OpenAIModel.__name__)
    print(InferenceClientModel.__name__)
    print(OPENAI_MODEL_ID)
    print(HF_MODEL_ID)
```

For OpenAI's first-party API, choose `OpenAIModel`. Its constructor accepts `model_id`, `api_base`, `api_key`, `organization`, `project`, and `client_kwargs`, alongside a few message-format options (installed source, `models.py:1646-1798`). In the normal path, set `OPENAI_API_KEY` in the environment and pass the model identifier. The current `openai` SDK, installed here as `openai==2.52.0`, supplies the key when `api_key` is omitted.

`api_base=` is a constructor argument, not a cue to invent a new environment variable. It lets you point the OpenAI-shaped client somewhere else. Keep `client_kwargs` for client settings that don't deserve their own smolagents argument, such as a timeout policy or a transport option. Keep `api_key` out of source and logs.

Anthropic has a different path in this release. No `AnthropicModel` exists in smolagents 1.26.0. Use `LiteLLMModel(model_id="anthropic/small-anthropic-model")`; the `anthropic/` prefix tells LiteLLM which provider adapter to use. The installed `anthropic==0.120.2` package is available for direct SDK work, but your smolagents model choice remains `LiteLLMModel` (installed source, `models.py:1205-1362`).

Choose `AzureOpenAIModel` for an Azure OpenAI deployment. It is a provider-specific class with Azure endpoint and authentication settings. That is a different decision from `OpenAIServerModel`: Azure OpenAI is a named provider integration, while the server variant is for an OpenAI-compatible endpoint whose ownership or routing is outside the first-party OpenAI path.

Choose `AmazonBedrockModel` for AWS Bedrock. Choose `AmazonBedrockServerModel` when the endpoint is exposed through an OpenAI-shaped server route rather than the provider-specific Bedrock integration. The names are close because the server class reuses the provider parent, but the deployment and credential story differ.

## Point at compatible servers

The `*ServerModel` family is for an OpenAI-compatible endpoint. `OpenAIServerModel` covers hosted or self-hosted services such as LM Studio, a vLLM server, llama.cpp, or another service that accepts the OpenAI chat request shape. Give it `model_id`, `api_base`, and the credential expected by that endpoint. The `api_base` value is the important part; a model name alone doesn't redirect a request (installed source, `models.py:1646` and the server-class method-resolution paths).

`AzureOpenAIServerModel` and `AmazonBedrockServerModel` are the provider-named server variants. They preserve provider-specific constructor behavior while allowing an OpenAI-compatible route. Don't substitute `OpenAIModel` for every endpoint because the class name sounds close. Select the class according to the endpoint's protocol and authentication contract.

## Run local runtimes

Local inference keeps prompts and responses on your machine, but it trades network dependence for hardware and setup. `TransformersModel` loads a model through Hugging Face Transformers in the Python process. It needs the `transformers` and `torch` stack plus enough CPU memory or GPU (graphics processing unit) memory for the weights.

`VLLMModel` belongs with a vLLM server and a graphics processing unit (GPU) with CUDA (NVIDIA's Compute Unified Device Architecture for GPU computing) support. It suits a machine that already has the CUDA and vLLM runtime prepared. `MLXModel` is the Apple Silicon route through MLX, so it isn't a cross-platform fallback for Windows or Linux. These three classes extend `Model` directly (installed source, `models.py:633-1137`).

Local runtimes can improve privacy and avoid per-request provider charges, but the model load can take time and your laptop becomes the uptime boundary. Hosted APIs add a network round trip and provider availability to each run, but they remove the need to carry model weights and a compatible GPU. Compare cost, privacy, latency, uptime, and quality against your own tasks. Quality depends on the task and test set, not on a universal ranking.

## Route roles to backends

A team rarely needs one model everywhere. A manager that classifies a request can use a fast, low-cost model. A specialist that reads a long source or writes code can use a stronger model with a larger context window. A reviewer can use a separate model so the review is not identical to the draft. Each `CodeAgent` receives its own `model=` object, so the role decision stays local to that agent's constructor.

`LiteLLMRouterModel` handles a different need: multiple provider entries and automatic fallback. `LiteLLMModel` represents the single-provider adapter selected by a `provider/model` identifier. The router accepts a model list and can move to another entry when the primary path fails. Use that extra routing surface when failover is a concrete requirement, not as a default wrapper around one provider.

At project scale, ch-18 uses `OpenAIModel` as its primary backend and HF Inference as its fallback. ch-19 extends the same factory idea to per-role backend selection, so the manager, researcher, writer, and reviewer can each receive a backend suited to its work.

## Build the factory

Start with a map from configuration keys to class constructors. Returning constructors instead of instances keeps the selection check offline and leaves credentials, model identifiers, and endpoint settings at the point where you build the real agent.

```python
from smolagents import (
    InferenceClientModel,
    LiteLLMModel,
    Model,
    OpenAIModel,
    TransformersModel,
)

MODEL_CLASSES: dict[str, type[Model]] = {
    "openai": OpenAIModel,
    "anthropic": LiteLLMModel,
    "hf": InferenceClientModel,
    "local": TransformersModel,
}


def pick_model(name: str) -> type[Model]:
    try:
        return MODEL_CLASSES[name]
    except KeyError as error:
        choices = ", ".join(sorted(MODEL_CLASSES))
        raise ValueError(f"Unknown backend {name!r}; choose {choices}") from error


if __name__ == "__main__":
    for backend_name in ("openai", "anthropic", "hf", "local"):
        model_class = pick_model(backend_name)
        print(f"{backend_name}: {model_class.__name__}")
```

The output proves the factory selected the intended class without creating a client or making a network call:

```text
openai: OpenAIModel
anthropic: LiteLLMModel
hf: InferenceClientModel
local: TransformersModel
```

In application code, add a small builder beside this map when each class needs different keyword arguments. For example, the OpenAI branch can call `OpenAIModel(model_id=MODEL_ID)` and rely on `OPENAI_API_KEY`; the Anthropic branch can call `LiteLLMModel(model_id="anthropic/...", api_key=os.getenv("ANTHROPIC_API_KEY"))`; the HF branch can call `InferenceClientModel(model_id=HF_MODEL_ID)` and rely on `HF_TOKEN`; and the local branch can call `TransformersModel(model_id=LOCAL_MODEL_ID)`. The factory chooses the class; configuration supplies the arguments.

## Avoid four beginner errors

**Instantiate `ApiModel` directly.** It is an abstract API-backed class, not a provider. Constructing it leaves the client behavior undefined. Pick a concrete child such as `OpenAIModel` or `InferenceClientModel`.

**Hardcode an API key.** A literal key can enter source control, terminal history, or a run log. Put `OPENAI_API_KEY`, `HF_TOKEN`, or `ANTHROPIC_API_KEY` in the environment and read it at runtime. If you pass a key explicitly, pass the environment value, not the secret text.

**Use the wrong provider class.** An Anthropic key does not turn `OpenAIModel` into an Anthropic client. Use `LiteLLMModel` with the `anthropic/` model prefix. Use `AzureOpenAIModel` for an Azure deployment and `AmazonBedrockModel` for Bedrock rather than assuming every hosted API has the same request contract.

**Forget `api_base=` for self-hosting.** A local service can speak the OpenAI request shape and still listen at a non-default address. Pass its base URL to `OpenAIServerModel`. Without `api_base=`, the request goes to the wrong destination or fails before the agent loop begins.

## Check the selection map

Run the factory block with the venv interpreter. It needs no API key, model download, GPU, or network access. Once those four printed class names match the expected output, replace the stub's class lookup with a builder only where your project needs provider-specific arguments. This separation lets your offline tests verify routing before a live credential is involved.

Backend choice also affects observability and safety. Keep the selected class, model identifier, endpoint label, and role in your run metadata, but redact credentials. If a hosted backend receives sensitive research text, record that residency decision. If a local runtime has a shared server, record who can reach it. A backend is part of the agent's boundary, not a hidden implementation detail.

> **The move:** Build a `backend_for(name)` factory that returns the right model class for `"openai"`, `"anthropic"`, `"hf"`, or `"local"`; instantiate your choice with `model_id=<small default>`; pass the model into a `CodeAgent`; and confirm the runnable test logs the class name without hitting a network. Then add `OpenAIServerModel(api_base=...)` as the path for any OpenAI-compatible endpoint you host yourself.
