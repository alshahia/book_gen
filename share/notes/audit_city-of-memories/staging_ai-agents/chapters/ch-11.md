# Chapter 11 — Guide Agents with Instructions and Memory

A terminal prints the agent's final answer after a short `.run(...)` call, and you wonder how to shape its behavior. The same `CodeAgent` constructor accepts a paragraph of house style, a re-plan timer, a step budget, and two knobs that control whether the next call remembers the last one. This chapter walks each.

Coming from ch-10: you built a `@tool` function with type hints and a docstring, watched the framework pass its return value through unchanged, and read four beginner errors to avoid. This chapter turns the same `CodeAgent` constructor into a configurable shape and adds the four knobs that control house style, re-planning, the step budget, and multi-turn memory.

## instructions adds guidance

Pass `instructions="..."` to `CodeAgent` to add a short paragraph of guidance to the system prompt. The framework passes your string under the Jinja variable name `custom_instructions`, and the default system prompt renders it inside a conditional block placed between the final numbered rule and the literal `Now Begin` line.

Verified against the installed smolagents==1.26.0 source at `agents.py:1271` on 2026-08-01: one short all-caps greeting instruction grew the rendered system prompt by exactly 25 characters, confirming the insertion is one conditional block. Pass a paragraph and the framework keeps it; pass `None` and the framework keeps its silence.

## prompt_templates swaps wholesale

That conditional block is the difference between `instructions` and a wholesale system-prompt swap. `system_prompt=` is not a constructor kwarg — passing it raises `TypeError` because the field lives inside `prompt_templates`, not on `MultiStepAgent.__init__` itself. The canonical override path is `prompt_templates={"system_prompt": ...}`, which makes the framework's default prompt — the tool menu, the Thought/Code/Observation loop, the eleven numbered rules, the `<end_plan>` tag instruction, and the `{% if custom_instructions %}` block — all disappear.

Verified at `agents.py:298-326` on 2026-08-01: a `CodeAgent(tools=[hello], model=stub(), max_steps=1, prompt_templates=custom)` whose `system_prompt` is the literal string `"CUSTOM ONLY"` produces a 63-character system prompt and the resulting step throws a parse error because the agent has no scaffolding to emit `<code>...</code>` blocks. The rule for now: use `instructions` to add guidance, and do not touch `prompt_templates`.

## Shape the prompt with `instructions`

The default system prompt is a single Jinja string stored on `prompt_templates["system_prompt"]`. It starts with the assistant framing, shows the Thought/Code/Observation cycle, lists three worked examples in `<code>...</code>` tags, then lists eleven numbered rules, then conditionally appends your `custom_instructions`, then ends with the literal `Now Begin` line.

Two sibling sub-templates travel with the system prompt: a `planning` sub-template that drives the model's re-plan step with the `<end_plan>` stop sequence, and a post-step recovery sub-template used when a step throws. The three pieces together describe a worker, give it a tool menu, and tell it how to re-survey what it knows. The chapter does not ask you to author Jinja.

## Add re-plan steps with `planning_interval`

`planning_interval` is the optional cadence at which the framework injects a `PlanningStep` into the ReAct loop. The default is `None`, which means no periodic re-planning. Pass an integer and the framework runs a planning step before action 1, then again before action `N+1`, `2N+1`, and so on, where `N` is your cadence.

Verified against `_run_stream` at `agents.py:550-552` on 2026-08-01: the trigger condition reads `if self.planning_interval is not None and (self.step_number == 1 or (self.step_number - 1) % self.planning_interval == 0)`. Each planning step is an extra model call that costs input tokens for the step history and output tokens for a written plan, in exchange for a structured chance to re-survey and pick a new path.

The beginner rule is to leave `planning_interval=None` until a task demonstrably needs more than ten steps; then try `planning_interval=5` or `planning_interval=10` and watch the token bill. For very long tasks the framework's `max_steps=20` ceiling is the harder limit; `planning_interval` is a quality knob, not a safety knob.

## Override the prompt with `prompt_templates`

`provide_run_summary` defaults to `False` and looks like a "print a summary at the end" switch. It does not fire on a top-level `.run()` call. The framework consumes it only inside `MultiStepAgent.__call__`, which is invoked when this agent is called as a managed agent by a parent agent's tool dispatch.

Verified at `agents.py:884-889` on 2026-08-01: when a parent agent invokes a managed child, the child's `__call__` runs `self.run(full_task)` and wraps the answer with `managed_agent.report`. If `provide_run_summary=True`, a `<summary_of_work>...</summary_of_work>` block built from `write_memory_to_messages(summary_mode=True)` is appended. The chapter's standalone agents are never invoked this way, so the flag is invisible to you here.

## Inspect runs with `return_full_result`

By default `.run()` returns the bare final answer as `Any`, so it may be a string, number, or another Python value. Pass `return_full_result=True` and the same call returns a `RunResult` dataclass instead; its `output` is also `Any`. The dataclass also carries `state` (the literal string `"success"` or `"max_steps_error"`), `steps` (the full `list[dict]` of `MemoryStep` records from `AgentMemory.get_full_steps()`), `token_usage` (a `TokenUsage` or `None`), and `timing` (a `Timing` with `start_time`, `end_time`, and a read-only `duration`).

Verified at `agents.py:196-254` on 2026-08-01: the dataclass also carries a deprecated `messages` accessor that warns `FutureWarning` and resolves to `RunResult.steps`. Don't read it. A `RunResult.dict()` method returns a JSON-serializable summary, which the ch-14 testing chapter will use. Per-call `return_full_result=None` falls back to the agent's constructor default, so one call can flip the mode without rebuilding the agent.

## max_steps caps the step count

`max_steps` is the agent's safety ceiling in 1.26.0 — a step count, not a wall-clock duration. The constructor default is `20`. Both `CodeAgent` and `ToolCallingAgent` forward the kwarg to `MultiStepAgent.__init__` at `agents.py:300`. When the loop exhausts the budget, the framework raises `AgentMaxStepsError` and `.run()` returns a `RunResult` with `state="max_steps_error"`.

A whole-package grep on 2026-08-01 confirms there is no `max_duration`, no `timeout_seconds`, and no wall-clock bound on the agent loop. The only related symbol is `RunResult.timing`, which measures how long a finished run took but does not limit it.

If you genuinely need a wall-clock limit, prefer a thread with a watchdog that sets a flag the agent checks each step. `asyncio.wait_for` and `concurrent.futures` timeouts stop your waiting, not the agent's execution; cancelling the future does not terminate the underlying worker.

## Memory grows within a run

The framework keeps a single `AgentMemory` on each agent (`agent.memory`) with two parts: a `SystemPromptStep` and a growing `list[MemoryStep]`. Within a single `.run()` call, the framework appends a `TaskStep` first, then interleaves `PlanningStep`s whenever `planning_interval` fires with one `ActionStep` per action iteration. The run ends with the final `ActionStep`, which carries the model's tool-call observation; no separate `FinalAnswerStep` is appended to `agent.memory.steps`.

Across separate `.run()` calls, the default `reset=True` clears the previous run's steps before the new `TaskStep` is appended. Verified on 2026-08-01: two consecutive `agent.run("task 1")` and `agent.run("task 2")` calls each leave `len(agent.memory.steps) == 3`, not a growing list. The `system_prompt` is recomputed each time `self.system_prompt` is read, so changes to `instructions` between calls take effect on the next run.

Write each `.run()` call to be self-contained by default. The `agent.memory.steps` snapshot is the chapter's inspection handle, and `reset=False` is the lever for explicitly continuing a multi-turn conversation within the same Python process. Don't reach for cross-call memory until you have a reason to.

## Continue conversations with `reset=False`

smolagents 1.26.0 does not have a `chat_messages=` parameter on `.run()`. Verified on 2026-08-01: the exact signature has eight parameters — `task`, `stream`, `reset`, `images`, `additional_args`, `max_steps`, `return_full_result`, and `self` — and there is no `chat_messages`, no `prior_messages`, no `history`. Multi-turn within one Python process happens by calling `.run()` multiple times on the same agent.

Pass `reset=False` to keep the prior conversation in `agent.memory.steps`; the next model call sees the previous history rebuilt by `write_memory_to_messages()`. Pass `additional_args={"key": value}` to inject fresh state for that one call: the framework updates `agent.state` with the dict and appends a literal "You have been provided with these additional arguments..." notice to the task string.

## Build your own persistence layer

smolagents 1.26.0 does not ship a built-in serialize-and-reload story for an agent's runtime state. The framework's `to_dict()` and `save()` machinery ship an agent template (the class, the tool sources, the prompt templates, the `max_steps`, the `planning_interval`) to disk or to a Hub Space, but the resulting `agent.json` does not contain `agent.memory.steps`, `agent.state`, the active `task`, or `instructions`.

Verified on 2026-08-01 against `to_dict()` at `agents.py:970-1008`: the dict keys are `class`, `tools`, `model`, `managed_agents`, `prompt_templates`, `max_steps`, `verbosity_level`, `planning_interval`, `name`, `description`, and `requirements`. No `memory`, no `state`, no `task`, no `instructions`. The chapter's persistence recipe for beginners is the simplest one: persist the task input and the final answer with `json.dumps({"task": task, "answer": str(answer)}, indent=2)`, and rebuild the agent from its template on the next run.

Don't reach for `pickle` on a live `MultiStepAgent` to round-trip the conversation; the live `state` dict holds references to the model's API client and the executor's open resources, and unpickling those across processes is not a recipe the chapter will endorse.

## Four beginner errors

These four failures show up before any advanced feature. Name the failure, then apply the smallest fix.

1. **Putting too much in `instructions`.** A 5,000-character `instructions` block dilutes the tool menu and the eleven numbered rules, and a small model loses focus after about a page of policy text. Cap `instructions` at one short paragraph (roughly 400 characters) and tell yourself that more is worse.

2. **Replacing `system_prompt` instead of using `instructions`.** Wholesale replacement strips the tool menu, the Thought/Code/Observation loop wording, and the conditional `custom_instructions` block; the agent then either ignores its tools or fails to emit parseable code. Treat `prompt_templates` as read-only until a later chapter introduces it deliberately.

3. **Expecting the agent to remember across separate `.run()` calls.** The default `reset=True` clears the previous run's steps before the new `TaskStep` is appended, so two consecutive calls do not share context. Fix: pass `reset=False` deliberately (and only when the same agent should continue) or pass the prior context as `additional_args`.

4. **Setting `max_steps` too low.** `max_steps` budgets action-loop iterations, not planning calls. Planning calls happen alongside the action loop and add token spend and latency without consuming the action-step budget. Start with `max_steps=10` for runnable examples. If you set `planning_interval=4` and `max_steps=20`, you'll see up to 20 action steps and up to 5 planning steps over the same run.

## Configure an agent with these knobs

The first runnable extends the ch-10 agent by passing `instructions`, `max_steps`, and `planning_interval` to the constructor. The example uses the same `add` `@tool` from ch-09 plus a paragraph of house style; full execution short-circuits on `load_api_key("HF_TOKEN")` until the reader has a token, the same guard ch-07 and ch-09 taught.

```python
import os

from smolagents import CodeAgent, InferenceClientModel, tool

MODEL_ID = os.getenv(
    "HF_AGENT_MODEL",
    "Qwen/Qwen2.5-Coder-7B-Instruct",
)  # pick any small coder model your HF_TOKEN can call


@tool
def add(a: float, b: float) -> float:
    """Add two numbers and return the sum.

    Args:
        a: The first number.
        b: The second number.
    """
    return a + b


def load_api_key(name: str) -> str:
    token = os.getenv(name)
    if not token:
        raise SystemExit(f"Set {name} in .env or your shell.")
    return token


def main():
    load_api_key("HF_TOKEN")
    agent = CodeAgent(
        tools=[add],
        model=InferenceClientModel(model_id=MODEL_ID),
        instructions=(
            "Show your arithmetic step before evaluating it. "
            "Keep replies under three sentences."
        ),
        max_steps=8,
        planning_interval=4,
    )
    result = agent.run("Use add to compute 2 + 3.", return_full_result=True)
    print(result.output)
    assert result.output == 5


if __name__ == "__main__":
    main()
```

## Two runs on the same agent

The second runnable shows a multi-turn pattern: call `.run()` twice on the same agent, where the second call uses `reset=False` and `additional_args` to keep the prior conversation and inject a fresh variable. `additional_args` updates `agent.state` and appends a literal notice to the task string; the model reads the string on the next iteration.

```python
import os

from smolagents import CodeAgent, InferenceClientModel, tool

MODEL_ID = os.getenv(
    "HF_AGENT_MODEL",
    "Qwen/Qwen2.5-Coder-7B-Instruct",
)  # pick any small coder model your HF_TOKEN can call


@tool
def add(a: float, b: float) -> float:
    """Add two numbers and return the sum.

    Args:
        a: The first number.
        b: The second number.
    """
    return a + b


def load_api_key(name: str) -> str:
    token = os.getenv(name)
    if not token:
        raise SystemExit(f"Set {name} in .env or your shell.")
    return token


def main():
    load_api_key("HF_TOKEN")
    agent = CodeAgent(
        tools=[add],
        model=InferenceClientModel(model_id=MODEL_ID),
        max_steps=6,
    )
    first = agent.run("Use add to compute 2 + 3.")
    second = agent.run(
        "Now add the previous result to 10.",
        reset=False,
        additional_args={"previous_answer": first},
    )
    print(first)
    print(second)


if __name__ == "__main__":
    main()
```

A short offline check exercises the result type without a provider call. The stub returns a literal `42`, so `agent.run(...)` produces the string `"42"` and the assertion holds:

```python
from smolagents import ChatMessage, CodeAgent, Model

class Stub(Model):
    def generate(self, messages, **kwargs):
        return ChatMessage(role="assistant", content='<code>final_answer("42")</code>')

with CodeAgent(tools=[], model=Stub(), max_steps=1) as agent:
    result = agent.run("Return 42.")
print(result)
assert result == "42"
```

The agent prints its step trace on the way through, so the terminal shows the standard `New run / Step 1 / Executing parsed code` boxes ending with `Final answer: 42`, and the final visible line is the value `print(result)` writes:

```text
42
```
