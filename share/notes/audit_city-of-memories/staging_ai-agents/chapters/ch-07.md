# Chapter 7 — Call Models Safely from Python

You have a chat completion API key sitting in a `.env` file. The next move is to wire it into a runnable script that posts a JSON body, reads the JSON reply, passes an explicit timeout, retries on 429 and 5xx, and catches auth and bad-request errors clearly.

## See HTTP mechanics with stdlib first

Start with the Python standard library so the HTTP plumbing shows up. The Python Software Foundation's `urllib.request` module ships with every Python install; a single chat-completion POST fits in about ten lines and needs no `pip install`.

```python
import json
import os
import urllib.request

URL = "https://api.openai.com/v1/chat/completions"
TIMEOUT = 30
MODEL = os.getenv("OPENAI_MODEL", "gpt-4o-mini")  # pin to whatever your account currently supports
PAYLOAD = {
    "model": MODEL,
    "messages": [{"role": "user", "content": "Say hi"}],
}


def chat_completion(api_key: str) -> dict:
    req = urllib.request.Request(
        URL,
        data=json.dumps(PAYLOAD).encode("utf-8"),
        headers={
            "Content-Type": "application/json",
            "Authorization": f"Bearer {api_key}",
        },
        method="POST",
    )
    with urllib.request.urlopen(req, timeout=TIMEOUT) as resp:
        return json.loads(resp.read().decode("utf-8"))


if __name__ == "__main__":
    # from ch07_helpers import load_api_key  # uncomment if saved to a shared module
    body = chat_completion(load_api_key("OPENAI_API_KEY"))
    print(body["choices"][0]["message"]["content"])
```

The pattern is the same one every chat-completion API uses: build a `Request` whose `data=` is the JSON body, send it with `urllib.request.urlopen`, and read `resp.read()` for the response. The `headers` dict carries the `Content-Type` and the bearer token the API needs to identify the caller. Each example below defines a `MODEL = os.getenv("OPENAI_MODEL", "gpt-4o-mini")` constant at the top — set `OPENAI_MODEL` in your shell or `.env` to pin to whatever your account currently supports.

## Skip to `http.HTTPStatus` for readability

Compare status codes against the named constants in `http.HTTPStatus` rather than raw numbers. The stdlib's `http` module ships an enum that names every status an API returns; beginners read `HTTPStatus.TOO_MANY_REQUESTS` and understand 429, while the same reader can miss `429` if `Retry-After` is on the next line.

```python
import http

status = resp.status  # e.g. 429
if status == http.HTTPStatus.TOO_MANY_REQUESTS:
    wait_seconds = int(resp.headers["Retry-After"])
    time.sleep(wait_seconds)
```

The mapping is one-to-one: `HTTPStatus.OK == 200`, `HTTPStatus.UNAUTHORIZED == 401`, `HTTPStatus.TOO_MANY_REQUESTS == 429`, `HTTPStatus.INTERNAL_SERVER_ERROR == 500`. The fetch above returns `resp.status` already, so swapping `429` for `http.HTTPStatus.TOO_MANY_REQUESTS` costs nothing.

## Switch to `requests` for cleaner code

The stdlib version works, but four extra lines of header-dict and encode-and-decode are not adding safety. The `requests` package shrinks the call site from ten lines to three. The `requests==2.34.2` release (verified against the requests quickstart and advanced-usage pages) is MIT-licensed and requires Python 3.10 or newer — the book's floor from ch-02 — so there is no version or license blocker.

```python
import os
import requests

URL = "https://api.openai.com/v1/chat/completions"
TIMEOUT = 30
MODEL = os.getenv("OPENAI_MODEL", "gpt-4o-mini")  # pin to whatever your account currently supports


def chat_completion(api_key: str) -> dict:
    response = requests.post(
        URL,
        json={
            "model": MODEL,
            "messages": [{"role": "user", "content": "Say hi"}],
        },
        headers={"Authorization": f"Bearer {api_key}"},
        timeout=TIMEOUT,
    )
    response.raise_for_status()
    return response.json()


if __name__ == "__main__":
    # from ch07_helpers import load_api_key  # uncomment if saved to a shared module
    body = chat_completion(load_api_key("OPENAI_API_KEY"))
    print(body["choices"][0]["message"]["content"])
```

`requests.post(json=...)` does the JSON encoding; `response.json()` parses the body; `response.raise_for_status()` converts any 4xx or 5xx into a `requests.exceptions.HTTPError`. The two footguns beginners fall into are already in this snippet: `timeout=` is required (without it `requests` blocks indefinitely), and `raise_for_status()` must come first or `.json()` will crash on an HTML error page.

## Load the key from `.env`, never source

The chat-completion call needs an API key, but the key must never live inside the script. Python's `os.getenv()` reads from the environment, and `python-dotenv`'s `load_dotenv()` populates that environment from a local `.env` file before the script runs.

```python
import os
from dotenv import load_dotenv


def load_api_key(name: str) -> str:
    load_dotenv()  # reads ./.env, walks upward, sets os.environ
    api_key = os.getenv(name)
    if not api_key:
        raise SystemExit(f"Set {name} in .env or your shell before running this.")
    return api_key


if __name__ == "__main__":
    api_key = load_api_key("OPENAI_API_KEY")
    print(f"loaded key of length {len(api_key)}")
```

The `python-dotenv==1.2.2` release defaults to "production wins over local file" — a real environment variable set in the shell is preserved unless `override=True` is passed. A newcomer can run the script with a developer's local `.env`, then ship the same code to production with a real secret in the shell, and the script picks up whichever value is present.

The `os.getenv(...)` form plus the explicit missing-key check is the safe form. Sending `Authorization: Bearer ` (with nothing after "Bearer") to a server never produces a useful error message and wastes a round trip; the explicit check fails loudly before any network call is made. Use `os.getenv(...)` rather than `os.environ[...]` so the missing-key check decides between an empty key and a missing key without raising `KeyError`.

## Match the body to ch-06's three roles

The body this chapter sends is the same three-role conversation ch-06 already established. A system message carries standing instructions, a user message carries the question, and an assistant message carries the model's prior reply. The Anthropic Messages API takes the system text as a top-level `system` parameter (per the Anthropic Python SDK reference, github.com/anthropics/anthropic-sdk-python); OpenAI's Chat Completions code keeps the standing instructions inside the `messages` list (per the OpenAI Python SDK reference, github.com/openai/openai-python).

```python
import os
import requests

URL = "https://api.openai.com/v1/chat/completions"
TIMEOUT = 30
MODEL = os.getenv("OPENAI_MODEL", "gpt-4o-mini")  # pin to whatever your account currently supports


def post_messages(messages: list[dict], api_key: str) -> str:
    response = requests.post(
        URL,
        json={"model": MODEL, "messages": messages},
        headers={"Authorization": f"Bearer {api_key}"},
        timeout=TIMEOUT,
    )
    response.raise_for_status()
    return response.json()["choices"][0]["message"]["content"]


if __name__ == "__main__":
    # from ch07_helpers import load_api_key  # uncomment if saved to a shared module
    api_key = load_api_key("OPENAI_API_KEY")
    messages = [
        {"role": "system", "content": "Answer in two short paragraphs."},
        {"role": "user", "content": "What is a context window?"},
    ]
    print(post_messages(messages, api_key))
```

The exact base URL, the exact field names, and the exact model identifier strings change every API version. Treat them as age-risk: this chapter teaches the pattern (build a messages list, send it as JSON, read the assistant's reply) and tells the reader to verify against the current provider reference before each book revision.

## Pass `timeout=` on every call

Every HTTP client in this chapter can hang indefinitely without an explicit timeout. `urllib.request.urlopen(req, timeout=30)` takes a single number in seconds for the entire blocking operation; the stdlib docs warn that without `timeout=` the call can wait forever. `requests` makes the same warning in stronger wording and accepts either a single float or a `(connect_timeout, read_timeout)` tuple.

The openai and Anthropic Python SDKs default to a much longer timeout tuned for batch jobs, not interactive loops. The SDKs accept an explicit override, and `client.with_options(timeout=20.0)` is the form documented in the OpenAI Python SDK reference (github.com/openai/openai-python) and the Anthropic Python SDK reference (github.com/anthropics/anthropic-sdk-python); ch-09 covers the SDK constructor.

```python
response = requests.post(URL, json=payload, headers=headers, timeout=30)
```

That single `timeout=30` line is the entire rule. Do not omit it. For a chat-completion call against a single provider, start with 30 seconds; for an inner agent loop where the model is supposed to answer quickly, 10 seconds is a more appropriate starting point.

## Retry on 429 and 5xx with backoff

The stdlib does not include a retry helper, so the chapter's retry loop is a short `for` over a small backoff. Transient failures (network blips, momentary 503s) recover cleanly after a delay; permanent failures (auth errors, bad-request bugs) should fail loudly the first time.

```python
import os
import time
import random

MAX_ATTEMPTS = 4
MODEL = os.getenv("OPENAI_MODEL", "gpt-4o-mini")  # pin to whatever your account currently supports


def call_with_retries(api_key: str) -> dict:
    payload = {
        "model": MODEL,
        "messages": [{"role": "user", "content": "Say hi"}],
    }
    for attempt in range(MAX_ATTEMPTS):
        try:
            response = requests.post(
                URL,
                json=payload,
                headers={"Authorization": f"Bearer {api_key}"},
                timeout=TIMEOUT,
            )
            response.raise_for_status()
            return response.json()
        except requests.exceptions.HTTPError as exc:
            code = exc.response.status_code if exc.response is not None else 0
            if code != 429 and code < 500:
                raise  # 4xx other than 429: programming bug, do not retry
            wait = (2 ** attempt) + random.uniform(0, 0.5)
            print(f"attempt {attempt + 1}: HTTP {code}, retrying in {wait:.2f}s")
            time.sleep(wait)
        except (requests.exceptions.ConnectionError, requests.exceptions.Timeout) as exc:
            wait = (2 ** attempt) + random.uniform(0, 0.5)
            print(f"attempt {attempt + 1}: network error ({type(exc).__name__}), retrying in {wait:.2f}s")
            time.sleep(wait)
    raise RuntimeError(f"max attempts {MAX_ATTEMPTS} reached")
```

The backoff doubles each try (1s, 2s, 4s, 8s) and adds a small `random.uniform(0, 0.5)` jitter so many concurrent clients do not retry at exactly the same instant. For projects with more than two or three retry sites, the `tenacity` package encodes the same policy as a decorator with composable building blocks (`stop_after_attempt`, `wait_random_exponential`, `retry_if_exception_type`, `reraise=True`); ch-11 picks tenacity up when structured workflows make the decorator worthwhile.

## Honor `Retry-After` on 429

HTTP 429 is the server's polite "slow down". IETF RFC 6585 §4 (and the broader RFC 7231 §7.1.3) lets the server answer with either a delay in seconds or an HTTP-date; reading the header beats guessing a backoff either way.

```python
import time
from datetime import datetime, timezone
from email.utils import parsedate_to_datetime


def parse_retry_after(value: str | None, attempt: int) -> float:
    """RFC 7231 §7.1.3 — Retry-After is integer seconds OR an HTTP-date. Cap at 60s."""
    if not value:
        return float(2 ** attempt)
    try:
        return min(60.0, max(0.0, float(int(value))))
    except ValueError:
        pass
    try:
        parsed = parsedate_to_datetime(value)
        if parsed is None:
            return float(2 ** attempt)
        delta = (parsed - datetime.now(timezone.utc)).total_seconds()
        return min(60.0, max(0.0, delta))
    except (TypeError, ValueError):
        return float(2 ** attempt)


if code == 429:
    retry_after = exc.response.headers.get("Retry-After")
    wait = parse_retry_after(retry_after, attempt)
    time.sleep(wait)
    continue
```

Without `Retry-After` the loop falls back to the exponential backoff above (start at 1s, double to a cap). Beginners should also know that 429s are normal during development: even a polite script that runs the same prompt ten times in a row can trip the rate limit, and the retry loop is what keeps that script polite.

## Sort errors into four buckets

The chapter's error model is exactly four categories, and each category deserves its own response. (1) Network errors — the request never reached the server; in `requests` these are `ConnectionError` and `Timeout`. Retry with backoff. (2) Auth errors — HTTP 401 (or 403); the key is missing, wrong, or revoked. Stop and tell the user.

(3) Bad-request errors — HTTP 400 (or 422 on Anthropic); the request itself was wrong. Stop and fix the code. (4) Server errors — HTTP 500, 502, 503, 504; the server is having a problem. Retry with backoff.

```python
def chat_completion_safely(api_key: str) -> dict:
    try:
        return call_with_retries(api_key)
    except requests.exceptions.HTTPError as exc:
        code = exc.response.status_code if exc.response is not None else 0
        if code in (401, 403):
            raise SystemExit("API key missing or invalid — check .env")
        if code in (400, 422):
            raise SystemExit(
                f"bad request (HTTP {code}): {exc.response.text[:200]}"
            )
        raise  # 5xx after retries is rare; let it propagate
    except requests.exceptions.ConnectionError as exc:
        raise SystemExit(f"network unreachable: {exc}")
```

The four-bucket model is the chapter's mental table. Every chat-completion client eventually needs an `except` arm that maps an HTTP code (or a typed SDK exception like `openai.RateLimitError`, `openai.APIStatusError`, `openai.APITimeoutError`, `openai.APIConnectionError`, per the OpenAI Python SDK reference, github.com/openai/openai-python) onto one of these four buckets. Mixing all four into one "retry everything" branch hides auth and bad-request bugs that should be loud.

## Keep keys out of source and git

Three rules, applied together. (1) Never put an API key in source code — `.py` files, notebook cells, and committed config files are all source. (2) Never check one into git — `.env` belongs in `.gitignore`, and a `.env.example` placeholder with the same key names and fake values gets committed instead so newcomers see the shape of the variables without seeing any real secret.

(3) Read the key from the environment at runtime through `os.getenv(...)` after `load_dotenv()` has populated `os.environ` from the local file.

```text
# .env (local-only, .gitignored)
OPENAI_API_KEY=sk-your-real-key-here
HF_TOKEN=hf-your-real-token-here
```

```text
# .env.example (committed, fake values)
OPENAI_API_KEY=
HF_TOKEN=
```

If a key is ever accidentally committed, the response is to revoke it at the provider immediately. Removing the file from a later commit does not erase it from the project's history; rotating the key is the only safe move, because every clone and every fork now potentially has the old secret.

## Loop the conversation by appending

The smallest useful chat-completion program holds the conversation as a Python list and appends the model's reply before the next call. The seed pattern is the same one ch-08's toy agent loop and ch-09's framework introduction will inherit.

```python
import os
from dotenv import load_dotenv
import requests

URL = "https://api.openai.com/v1/chat/completions"
TIMEOUT = 30
MODEL = os.getenv("OPENAI_MODEL", "gpt-4o-mini")  # pin to whatever your account currently supports


def send(messages: list[dict], api_key: str) -> str:
    response = requests.post(
        URL,
        json={"model": MODEL, "messages": messages},
        headers={"Authorization": f"Bearer {api_key}"},
        timeout=TIMEOUT,
    )
    response.raise_for_status()
    return response.json()["choices"][0]["message"]["content"]


def main() -> None:
    load_dotenv()
    api_key = os.getenv("OPENAI_API_KEY")
    if not api_key:
        raise SystemExit("OPENAI_API_KEY missing — add it to .env and re-run")
    messages = [
        {"role": "system", "content": "Answer in one short sentence."},
        {"role": "user", "content": "What is a context window?"},
    ]
    while True:
        user = input("you> ").strip()
        if user.lower() in {"quit", "exit"}:
            break
        messages.append({"role": "user", "content": user})
        reply = send(messages, api_key)
        print(f"model> {reply}")
        messages.append({"role": "assistant", "content": reply})


if __name__ == "__main__":
    main()
```

The `messages.append(...)` line is the seed. Tool-calling, function-calling, structured outputs, streaming, and multi-agent handoffs all grow out of that one line; the chapter holds them for ch-08 and beyond.

## Four beginner errors worth memorizing

The four control-flow-error analogs from ch-04 had a fix-each-in-one-line form. The four API-call errors look the same way.

**Missing `timeout=`** — `requests.post(url, json=payload)` without a `timeout=` argument can block forever if the server hangs. Traceback category: `KeyboardInterrupt` after a long hang, or `requests.exceptions.ReadTimeout` if your terminal session eventually wakes up. Fix: pass `timeout=` on every call; start with `30` and tune.

**Calling `.json()` without `raise_for_status()` first** — `response.json()` parses the body regardless of HTTP status, so an HTML error page from a 500 gives `json.JSONDecodeError` instead of an HTTP error. Traceback category: `requests.exceptions.JSONDecodeError` (or the standard `json.JSONDecodeError`). Fix: call `response.raise_for_status()` before `.json()`.

**Forgetting `.env` in `.gitignore`** — committing `.env` puts the API key in the project's history forever. Traceback category: no exception at runtime; the failure is at audit time when the maintainer reviews the diff. Fix: add `.env` to `.gitignore` and commit a `.env.example` placeholder with empty values.

**Sending an empty bearer token** — `requests.post(..., headers={"Authorization": "Bearer "})` returns a 401 with a confusing "missing API key" message from the server, which is more noise than signal. Traceback category: `requests.exceptions.HTTPError` with `401 Client Error`. Fix: read the key with `os.getenv(...)`, raise `SystemExit` if it is empty, then send the request.

## Check: a deliberately-broken endpoint loops then fails

A runnable check that exercises the four-bucket model without needing an API key: every attempt posts to a TEST-NET-1 IP (RFC 5737 — the documentation address block that never routes) so the loop lands in the network-error branch on each try. Cross-platform: Windows, macOS, and Linux all treat `192.0.2.1` as unrouted.

```python
import sys
import time
import random
import urllib.error
import urllib.request

URL = "http://192.0.2.1/chat/completions"
TIMEOUT = 0.5
MAX_ATTEMPTS = 3


def post_once():
    req = urllib.request.Request(
        URL,
        data=b'{"model":"x","messages":[]}',
        headers={"Content-Type": "application/json"},
        method="POST",
    )
    with urllib.request.urlopen(req, timeout=TIMEOUT) as resp:
        return resp.status, resp.read()


def call_with_retries(max_attempts: int = MAX_ATTEMPTS):
    last = None
    for attempt in range(max_attempts):
        try:
            status, _body = post_once()
            return ("ok", status)
        except urllib.error.HTTPError as exc:
            last = ("http", exc.code)
        except urllib.error.URLError as exc:
            last = ("network", str(exc.reason))
        wait = (2 ** attempt) + random.uniform(0, 0.25)
        print(
            f"attempt {attempt + 1}: {last[0]}={last[1]} -> wait {wait:.2f}s",
            file=sys.stderr,
        )
        time.sleep(wait)
    return ("exhausted", last)


if __name__ == "__main__":
    bucket, info = call_with_retries()
    print(f"final bucket={bucket} info={info}")
```

Run it. Expected output ends with `final bucket=exhausted info=('network', ...)` after three attempts, each printing a network-error line to stderr. The cross-platform guarantee is the only test the chapter needs: the network bucket is the right response when no route answers.
