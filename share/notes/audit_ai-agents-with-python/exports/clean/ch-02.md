# Chapter 2 — Set Up a Cross-Platform Workspace

By the end of this chapter, you have a working Python 3.10 or newer interpreter, a project folder with a `.venv` containing smolagents and JupyterLab, a `.gitignore` that excludes the virtual environment and any secrets file, and a `.env.example` template ready for the API keys ch-07 onward will need.



## Pick a recent Python 3.10 or newer

The smolagents PyPI project page lists "Requires: Python >=3.10" on its metadata, and the Python Software Foundation's "Active Python releases" page lists 3.10, 3.11, 3.12, 3.13, and 3.14 as the actively supported versions. Python 3.9 is end-of-life and will not run later chapters.

A sensible beginner default is the latest bugfix release of Python 3.13 — the most recent stable line with a long support window. Python 3.12 is the conservative pick if you need maximum third-party-package compatibility. Whichever you choose, write down the exact version once it is on disk. "Reinstall later" stays reproducible when the chapter and your interpreter match. The version in this book's `.venv` is Python 3.13.7.

## Install on Windows, macOS, or Linux

The Python Software Foundation gives different install paths per platform, and the Windows story changed materially in late 2025 when the Python Install Manager (an MSIX installer from python.org or the Microsoft Store) replaced the legacy "Python launcher for Windows" and the older full installer. **This section may age quickly** — if your Microsoft Store or python.org URL has moved, follow the Python Software Foundation's "Using Python on Windows" page linked from the downloads. Once installed, the `python` and `py` commands become available in any terminal, and CLI tools installed with pip (such as `jupyter`) land under `%LocalAppData%\Python\bin`, which the installer prompts you to add to `PATH`.

On macOS the recommended beginner path is the signed and notarised python.org `.pkg` installer. The package is a universal2 binary that runs natively on both Apple Silicon and Intel Macs from macOS 10.15 Catalina onward, and Gatekeeper accepts it because the Python Software Foundation signs the build. After installation, the version-specific binaries (for example `python3.14`) appear in `/usr/local/bin`, which is on the default shell `PATH`. Do not rely on `/usr/bin/python3` — Apple ships that on its own schedule and it is typically older than the version the book needs.

On Linux there is no single python.org installer. Python is usually pre-installed or one `apt install` / `dnf install` / `zypper install` / `apk add` away. If your distro ships Python 3.9 or lower, you have three realistic options: install a newer `python3.x` from a third-party source such as the `deadsnakes` PPA on Ubuntu, use pyenv to build a user-local interpreter, or build from source. The Python docs explicitly say distribution packages often lag the latest release, so pick the first option that does not require administrator privileges. The Python docs' "Using Python on Unix platforms" page is the canonical reference for your specific distribution.

## Build a project folder and a virtual environment

A virtual environment is a self-contained directory that holds a copy of the Python interpreter and the packages your project installs into it. The Python tutorial's "Virtual Environments and Packages" section recommends one per project, created with `python -m venv .venv`. The directory name `.venv` is the convention: the leading dot keeps the folder hidden on macOS and Linux, and the name avoids a collision with a future `.env` secrets file (the Python Packaging Authority's venv guide recommends the same `.venv` location).

Create a project folder, then a virtual environment inside it:

```bash
mkdir ai-agents-with-python
cd ai-agents-with-python
python -m venv .venv
```

Activation differs by platform. On Windows (PowerShell or cmd):

```bash
.venv\Scripts\activate
```

On macOS or Linux (bash or zsh):

```bash
source .venv/bin/activate
```

You can verify the environment is active by running `where python` on Windows or `which python` on macOS or Linux and confirming the path ends in `.venv`. The shell prompt also gains the venv name as a prefix. Running `deactivate` returns you to the system default.

## Install smolagents and JupyterLab

With the virtual environment active, every install runs through `python -m pip install <package>`. The Python Packaging Authority's "Install packages in a virtual environment using pip and venv" guide recommends this form because it guarantees the package lands inside the active `.venv` rather than the system Python. The same guide recommends pinning a version — `python -m pip install "smolagents==1.26.0"` — so the environment you build today is the environment you can rebuild next year.

JupyterLab is the notebook UI the book uses for exploratory examples. The JupyterLab chub entry warns that "JupyterLab only provides the UI and server shell; your code executes in a kernel environment," so the kernel and the project packages must live in the same `.venv`. Install JupyterLab and python-dotenv into the same venv as smolagents:

```bash
python -m pip install "smolagents==1.26.0" jupyterlab python-dotenv
```

The canonical launcher is `jupyter lab` from the project directory. If you prefer the classic notebook UI, the older `jupyter notebook` command is also available — both ship from the Jupyter organisation.

## Prefer `python -m <module>` over `python script.py`

The Python docs' "Command line and environment" section lists three ways to run Python from a terminal: `python script.py`, `python -m module`, and `python -c "code"`. The docs prefer `python -m` for two reasons. First, the launcher works regardless of the current directory's contents. Second, it cannot be hijacked by a same-named local file that would shadow a stdlib module — a beginner footgun the docs call out by example.

You will see `python -m` in this book from this chapter forward. `python -m venv` already used it. `python -m pip install` did too. Saved `.py` files exist for projects (ch-17, ch-18, ch-19), and inline snippets and library CLIs go through `python -m`. Notebook cells live in a different world: they run inside the JupyterLab kernel bound to the active venv.

## Keep secrets in a `.env`, never in code

API keys — Hugging Face tokens, OpenAI keys, anything else — belong in a `.env` file at the project root, never in source code and never in a notebook cell that ends up in git. The python-dotenv chub guide (1.2.2, 2026-03-12) documents the canonical pattern: call `from dotenv import load_dotenv; load_dotenv()` near the top of the script, and the package walks upward looking for a `.env`, parses its `KEY=value` lines, and copies them into `os.environ` without overriding real environment variables.

Two consequences follow. First, a `.env` file is local-only — it must be added to `.gitignore` so it never reaches a remote. Second, a `.env.example` placeholder file with the same key names but empty values gets committed instead, so newcomers see the shape of the variables without seeing real secrets. The python-dotenv chub guide's "Common Pitfalls" section names the rule directly: "Do not commit `.env` files with secrets. Add them to `.gitignore`."

Create the template file at the project root:

```dotenv
# Copy to .env and fill in real values. .env is gitignored; .env.example is committed.
HF_TOKEN=
OPENAI_API_KEY=
ANTHROPIC_API_KEY=
```

The `HF_TOKEN` line is the variable `InferenceClientModel` reads in ch-09. The OpenAI and Anthropic lines are reserved for ch-17's backend factory; the book does not need them yet, but adding them now keeps the template stable across chapters.

## Add the canonical Python `.gitignore`

The GitHub-curated `Python.gitignore` is the standard template. Create a `.gitignore` at the project root with these lines:

```gitignore
# Virtual environments
.venv/
venv/
env/

# Secrets
.env

# Python bytecode caches
__pycache__/
*.py[cod]
*$py.class

# Distribution / build
*.egg-info/
build/
dist/

# Jupyter checkpoints
.ipynb_checkpoints/
```

The `.venv/` entry covers your virtual environment. `.env` covers your secrets file. `__pycache__/` and `*.py[cod]` cover Python's bytecode caches. `.ipynb_checkpoints/` covers Jupyter's autosave folder. None of those files belong in git.

## Check: the venv imports smolagents

Run this from the project root with the virtual environment active:

```bash
python -c "import smolagents; print(smolagents.__version__)"
```

Expected output:

```
1.26.0
```

If the print reads `1.26.0`, the workspace is ready. If it raises `ModuleNotFoundError`, the virtual environment was not active when pip ran — re-activate with `.venv\Scripts\activate` on Windows or `source .venv/bin/activate` on macOS or Linux, then re-install.
