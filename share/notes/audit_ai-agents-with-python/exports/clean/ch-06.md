# Chapter 6 — Understand Language Models

Picture a chat box assembling one word at a time. In this chapter, you'll see why a language model produces only a stream of token-by-token guesses from a probability distribution it learned once during training. You'll also meet the context window, the three message roles, and two safety flags that travel through every later chapter.

## See the next-token loop in your head

A large language model is a statistical prediction machine. IBM's *What are LLMs?* page says the model "repeatedly predicts the next word in a sequence" by "calculating the probabilities for all potential next tokens" and "outputting the most likely one." That single sentence is the entire trick.

The loop runs once per token. The model takes every token it has seen so far, computes a probability over its vocabulary, samples one, appends it to the context, and repeats. The model's behavior changes with the context and with nothing else — there is no hidden notebook, no separate scratchpad, no second pass that reconsiders the whole answer.

The model does not know the final answer in advance. Every "clever" behavior an agent seems to exhibit is the result of running this loop many times with carefully chosen context.

Open a chat interface (the website of any major model provider) and ask it to explain in plain English what it does when it sees the word "cat". Compare its answer to this chapter's four-step description of next-token prediction.

## Meet tokens, the model's alphabet

Before the model can read text, that text has to be split into tokens — short pieces that look like a mix of whole words, word pieces, and single characters. The Hugging Face Transformers documentation on tokenization describes sub-word tokenization: common short words stay as one token, longer or rarer words split into recognizable sub-pieces, and previously unseen words can still be represented by recombining known sub-pieces.

Tokens are the model's alphabet. A sentence is not a sequence of characters and not a sequence of words; it is a sequence of tokens, and the model only ever sees the token stream. The number of tokens in a piece of text — not the number of characters or words — determines pricing, latency, and whether the text fits inside a context window.

The same sentence can produce different token splits on different models. For English, a rough rule of thumb is about 1.5 tokens per word, which is the only number the chapter asks you to remember.

## Distinguish training from inference

Training and inference are two different jobs, and an agent application only ever does the second one. IBM's *What is AI inference?* page frames training as the work a model vendor does once: feed the model enormous amounts of text, adjust the internal weights until the model is good at predicting the next token, then ship the result. Training is expensive, slow, and runs on hardware the developer of an agent does not own.

Inference is what every application does every time it calls the model. The same IBM page defines online inference as the flavor where "a trained model processes input data immediately, one input at a time" and labels it as "appropriate for any AI system whose outputs are time sensitive … or that require live interactions with users." Every `model.generate(prompt)` call in an agent application is online inference.

If you need many completions at once, sending them as a batch to the API is usually faster and cheaper than calling once per prompt — most providers support batch endpoints.

The asymmetry matters because the model is not running fixed code — it is sampling from a probability distribution, so the same prompt can produce different replies on different calls. The agent does not retrain; it only ever infers.

## Hold the context window in mind

The context window is the model's working memory, measured in tokens. IBM's *What is a context window?* page defines it as "the amount of text, in tokens, that the model can consider or 'remember' at any one time." Everything the model can see at one time — the system prompt, the prior turns of the conversation, any documents or tool results the agent has attached, and the question being asked right now — has to fit inside that single window.

When inputs grow past the window, the application has to drop, truncate, or summarize the older parts before sending the next call. The practical engineering response stays the same shape as the inputs grow: trim, summarize, and place important information near the start or end of the context.

Modern context windows are large enough to hold a few pages comfortably and small enough that a novel-length prompt would overflow; specific sizes change every quarter, so this chapter keeps the comparison directional. The IBM page also records the "Lost in the Middle" effect, where long-context models often use information near the start or end of the input more reliably than information buried in the middle. Place the key instructions and the question near the ends of the context.

## Shape sampling with temperature and top_p

The model is not picking a single "correct" token at every step; it is sampling from a probability distribution, and two settings shape how that sampling behaves. IBM's *What is LLM temperature?* page describes temperature as a parameter that "controls the randomness of text that is generated by LLMs during inference." A lower temperature makes the most likely tokens more likely; a higher temperature increases the chance of selecting a less probable token.

The same page defines `top_p` — nucleus sampling — as a way to "consider tokens whose cumulative probability is greater than a specified probability value." A common setting is 0.9 or 0.95, which restricts the model to the smallest set of tokens whose combined probability exceeds the threshold. Temperature and `top_p` are not independent; most providers recommend changing one at a time.

The beginner rule is to leave the defaults unless there is a reason to change them. Reach for a lower temperature when the agent needs a precise, reproducible answer (for example, calling a function with strict argument types) and for a higher temperature when the agent specifically wants to brainstorm. The chapter holds off on `top_k` and the other knobs — they exist, they are documented elsewhere, and they are not needed for the first programs in this book.

## Learn the three-role message convention

Modern chat-completion APIs all work the same way at a beginner level: the program sends a list of messages, and the model returns one new message in reply. Both document the same three roles, with a small naming wrinkle this chapter treats as a footnote rather than a central plot point.

A system (or developer) message carries standing instructions from the program author — "answer in two short paragraphs and never invent URLs." A user message carries the actual question or request from the human. An assistant message represents a past reply the model itself produced earlier in the same conversation. The system message has the highest priority, user messages have lower priority, and assistant messages are the model's own prior outputs.

Different providers name the system role differently and place it in different fields. Anthropic's Messages API takes a top-level `system` parameter with no role name on it at all. Older OpenAI Chat Completions code passes the standing instructions as the first message with role `system`; OpenAI's current Responses API renamed that role to `developer` while keeping the same priority. The chapter teaches the three-role pattern, not the exact parameter name; ch-07 translates the pattern into concrete code.

## Carry two safety flags forward

Two safety flags travel with you into every later chapter, and ch-06 is where they enter the book. The first flag restates the ch-01 draft-before-action rule for the model surface: the model can return biased, offensive, or otherwise harmful content because the training data contained it, and the agent's job is to treat LLM output as a draft, not as truth. Never pipe model text straight into an action with real-world side effects without a check.

The second flag is newer. IBM's *What is a context window?* page notes that "a longer context window might also have the unintended effect of presenting a longer attack surface for adversarial prompts," and points to Anthropic's *Many-shot jailbreaking* research showing that "increasing a model's context length also increases its vulnerability to 'jailbreaking' and (subsequently) being provoked to produce harmful responses." The same long window that lets the agent hold a long conversation also makes the model more vulnerable to adversarial text hidden in documents, tool results, or web pages.

The deeper defenses — sandboxing, scoped API keys, human approval, permission limits — belong in ch-15. For now: treat model output as a draft, and treat the model as a reader of any text the agent hands it. An agent that fetches web pages or accepts uploaded files is handing the model content the user did not write, and the agent author is responsible for filtering it.
