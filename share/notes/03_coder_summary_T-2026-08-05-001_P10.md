## WARNs surfaced

1. **HIGH — the spec'd npm package does not exist.** `npm view @goncalomb/languagetool-mcp` → **E404, not found on the registry**. Consequence: the `--lang` grammar row can never reach PASS/FAIL in production; it will always degrade to WARN. I set `"enabled": false` because an enabled entry makes opencode attempt a failing `npx` spawn on every startup for zero benefit; flipping it back is one keystroke once the name is resolved. Closest published alternative is `@dpesch/languagetool-mcp-server` (v1.1.0) — but it targets the LanguageTool **Pro API** (requires an API key, no local JVM, no auto-downloaded `ar` pack), a materially different deployment shape than the plan assumes. **Needs a master decision; I did not substitute it.**
2. **MEDIUM — the tool name `check_text` is unverified.** With no live server, the `tools/call` name and its argument keys (`text`, `language`) are my best-guess reconstruction. `_extract_issues` tolerates three response envelopes to blunt this, but the *request* side is untested against reality. Blocked by WARN 1.
3. **MEDIUM — status case deviates from the spec.** Spec §2 says `status: "pass"|"fail"` (lowercase); I emit **uppercase** `PASS`/`FAIL`. Rationale: all 8 existing rows are uppercase, `main()`'s exit-code logic keys off `r.status == "FAIL"`, and mixed casing in one `checks` array would break any consumer filtering on `.status=="FAIL"` (including the documented `jq` recipe). Both new tests assert case-insensitively (`r.status.lower()`), so a future flip to lowercase won't break them.
4. **LOW — spec silent on the transport-failure verdict.** I chose WARN (not FAIL) when the MCP is unreachable, so an optional external dependency can't block a chapter that passes all 8 built-in rules. Documented in SCRIPTS.md and the module docstring.
5. **Java/Node preconditions met on this host:** OpenJDK **17.0.17** and Node **v24.11.1** both present — so WARN 1 is purely a package-name problem, not an environment gap.
