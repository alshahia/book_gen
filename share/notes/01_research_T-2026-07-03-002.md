## Risks and doubts

### R1 — `scripts/validate-memory.sh` ships as "optional" but its absence silently breaks supersession
- **Severity:** medium
- **Mitigation:** Ship the linter in v0.13.0. ~50 LOC bash; checks: frontmatter has required keys, `superseded_by:` resolves to an existing file, `status` ∈ {active, superseded}, `scope` ∈ {global, project, role}, `created` is YYYY-MM-DD, `last_verified` is YYYY-MM-DD. Failure modes if missing: a `superseded_by:` pointing to a non-existent file silently misleads readers (writes land in the new file but readers still see the old).

### R2 — Write-hygiene: specialists skip the "Memory written:" line on non-substantive dispatches
- **Severity:** high
- **Why:** The locked design says "every dispatch contract gains a mandatory `Memory written:` (or `No memory write: <reason>`) line" (`share/handoffs/00_user_task_T-2026-07-03-002.md:30`). Specialists that finish a 30-second task will type `No memory write: trivial task` 100% of the time. That's correct usage, but it means the protocol's signal value is mostly noise.
- **Mitigation:** Distinguish substantive vs trivial dispatches. Only gate on `Memory written:` when the dispatch assigned substantive work (a real task with a deliverable, not a status check). Master should hard-gate only on dispatches that hit `tasks/<id>.md` rows. Document the threshold in the dispatch contract itself.

### R3 — Write-honesty: specialists write trivial fluff to satisfy the protocol
- **Severity:** medium
- **Why:** Once the protocol is mandatory, the failure mode flips from "they skip it" to "they write junk." A specialist that wrote a one-line "this task went fine" entry pollutes semantic memory.
- **Mitigation:** Define "durable insight" with testable criteria in each specialist's SKILL.md. Mandatory test:
  1. Would a different agent (or me, in 3 months) benefit from knowing this on re-entry? (Yes → write.)
  2. Is it derivable from `share/notes/03_coder_summary_*.md` or the source code? (Yes → don't write; cite the source instead.)
  3. Did I spend >30 seconds figuring it out, or did it contradict my prior expectation? (Yes to either → write.)
  Cap each entry at ~20 lines.

### R4 — Read-bloat: files grow, re-entry context budget blown
- **Severity:** high
- **Why:** 200 lines per scope × 3 scopes = 600 lines worst-case. With semantic memory accumulating across 6 specialists + master, that budget fills up. The "≥2 tasks before promoting to semantic" rule (per existing notes/READMEs, e.g. `agents_manager/research/notes/README.md:27`) helps but doesn't cap total size.
- **Mitigation:**
  - Cap TOTAL memory read on re-entry at 600 lines (200 × 3), hard. If a scope's `notes/` exceeds 200 lines, grep by task keyword first, then read up to 200 lines of matches.
  - 90-day sweep (`last_verified` older than 90 days → flag, don't auto-delete) is the right long-term lever; document the sweep criteria in master's Phase 5 close protocol.
  - One-line guardrail in the validator: per-scope file count × avg-line-count ≤ 200 lines × N files.

### R5 — Stale memory: agent trusts a no-longer-true entry
- **Severity:** medium
- **Why:** No automated sweep today. A `last_verified: 2025-03-15` entry can sit in the read path indefinitely. Specialists have no protocol for "this no longer applies" — they would write a new entry alongside the stale one.
- **Mitigation:** The 90-day sweep at Phase 5 close is the right mechanic. Also: every memory entry's TL;DR must end with a "Verify against:" line pointing to the source-of-truth (a `path:line`, a doc, or a test). When the source moves, the entry's stale-ness becomes mechanically detectable.

### R6 — Cross-project contamination: project-A memory used on project-B
- **Severity:** medium
- **Why:** Specialists read `agents_manager/<role>/notes/` unconditionally. If an operator worked on project A (which had a specific tech stack) and then switched to project B (different stack), the role memory will mislead.
- **Mitigation:** Two-layer defense:
  - The `scope: project` tag in frontmatter (`share/handoffs/00_user_task_T-2026-07-03-002.md:33`) lets the read-time grep filter by the active project slug.
  - The role-memory README in each specialist should say "always grep by `scope: project` and the active project slug before reading semantic entries; ignore semantic entries that reference a different project."

### R7 — Schema drift across 7 specialists' READMEs
- **Severity:** medium
- **Why:** Each specialist's `notes/README.md` is independently editable. With 7 places to update, they will diverge by month 3.
- **Mitigation:** Plan should produce ONE canonical `agents_manager/memory/README.md` as the schema source-of-truth. Per-role READMEs are 2-line pointers: "For schema, lifecycle, read/write protocol → `agents_manager/memory/README.md`. This folder is where this specialist writes `agents_manager/<role>/notes/{semantic,episodic}/`." Validator (`scripts/validate-memory.sh`) checks for schema-key consistency.

### R8 — Supersession gaps: `superseded_by` points to a nonexistent file
- **Severity:** low
- **Why:** The proposal includes supersession via `status: superseded` + `superseded_by:` link. If the link is wrong, the old entry looks stale but the new entry is never read.
- **Mitigation:** Validator checks `superseded_by:` resolves. Plan must include the validator as a release blocker for v0.13.0 (see R1).

### R9 — Cold-start tax: first-ever project gets nothing
- **Severity:** low
- **Why:** New operators get an empty scaffold. Until they (or their first task) write something, every re-entry is a no-op. They might mistake "no memory" for "memory not working."
- **Mitigation:** `agents_manager/memory/README.md` ships with 2-3 worked example entries in `agents_manager/memory/global/` so a fresh operator sees the shape. Optionally: the `bin/install.sh` could ship a small starter memory when `--memory-seed` is passed (deferred to v0.13.1+ to keep v0.13.0 minimal).

### R10 — Migration cost: downstream users who already have local files in `agents_manager/<role>/notes/`
- **Severity:** low
- **Why:** Most operators have empty folders (because the v0.12.0 README only documents the shape, not the population). But a power-user with content risks having it rendered invalid when the scaffold adds `.gitkeep` and README files (no actual content loss, but visual noise in `git status`).
- **Mitigation:** Scaffold is purely additive — it does not move or rename any existing file. `.gitkeep` and README only land where the folder was empty. Document the "no migration" stance in the CHANGELOG entry.

### R11 — Read-time cost: every specialist spends N tokens on re-entry even when nothing applies
- **Severity:** medium
- **Why:** Even with grep-first, a specialist always spends at least the cost of grepping + reading the first 20 lines of context. For a 200-line global memory, that's ~6 KB / ~2k tokens per dispatch. With 7 specialists × 1 dispatch per task = ~14k tokens per task on memory alone.
- **Mitigation:** Two layers:
  - Empty scaffold = 0 token cost (first task on a fresh clone).
  - 90-day sweep keeps the budget bounded as content grows.
  - In v0.13.0, this is acceptable cost for the value delivered; revisit at v0.15.x if metrics show re-entry memory growing >5% of total context.

### R12 — Master's `agents_manager/SKILL.md` edit is in-lane but is high-blast-radius
- **Severity:** medium
- **Why:** Master can edit its own SKILL.md via the "deliberate maintenance task" exception (`agents_manager/SKILL.md:496`). But the master's SKILL.md is 526 lines and is read on every task start; a wrong edit breaks the whole pipeline.
- **Mitigation:** Per `agents_manager/SKILL.md:496` "Editing `agents_manager/SKILL.md` during pipeline execution ... do not silently rewrite the protocol that defines the pipeline." The edit must go through am-coder dispatch (consistent with how `share/handoffs/00_user_task_T-2026-07-03-002.md:47` plans it). Master should NOT self-edit its own orchestration doc.

### R13 — The "no per-task model selection" override means we cannot tune specialist memory pressure by model
- **Severity:** low
- **Why:** Per `agents_manager/SKILL.md:311-313`, OpenCode does not currently support per-agent model selection. If a particular specialist is more memory-constrained (e.g. am-coder under a smaller context window), we cannot shrink that specialist's read budget independently.
- **Mitigation:** Defer. All 7 agents share the same 200-lines-per-scope budget for v0.13.0. Revisit when per-agent model selection is available.

The task requires editing 6 specialist SKILL.md files plus master's own.
