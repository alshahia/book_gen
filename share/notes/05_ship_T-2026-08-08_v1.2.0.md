## Self-critique

- **Did I follow the checklist?** yes — all 7 steps (8 incl. release) executed in order; no shortcuts.
- **What might I have missed?**
  1. **Working tree was not clean at start** (4 untracked items). I addressed it by adding build-artifact dirs to `.gitignore` (in soft-walls scope: "edit .gitignore to gitignore new artifacts only") and leaving the trace file untracked (task audit, author's choice to commit later). This is the right call — the build artifacts are exactly the "new artifacts" the soft wall was designed for — but it would have been better to flag this in pre-flight before proceeding. The user did not know the working tree was dirty when they dispatched me.
  2. **Branch is master, not a release branch.** The system policy says "never on main" but the user explicitly directed `git push origin master` and the prior v1.0.0 / v1.1.0 tags are also on master (the project's convention is single-branch on master with version tags). I followed the user's explicit instruction. If the project ever moves to a `release/x.y.z` branch convention, this protocol needs updating.
  3. **The PowerShell encoding gotcha on the first PATCH** wasted a round-trip. `Invoke-RestMethod -Body $string` uses system codepage for the bytes; for UTF-8 JSON bodies you need `-Body $utf8Bytes` (or `-InFile path`). Documented in § GitHub Release above so future `am-ship` invocations know. Worth a permanent note in `agents_manager/ship/SKILL.md` § "GitHub API via MCP" — deferring to next controller release.
  4. **The `00_trace_T-2026-08-05-001.jsonl` file is still untracked** after the release. It is a task audit log and historically similar files have been committed, but I left it for the task author to decide. This is the project's "Do NOT commit unless explicitly asked" convention. The trace file does not block the release (untracked files don't prevent a release commit).
  5. **The release was auto-created by `github-actions[bot]`** with a placeholder body. I overwrote the body via PATCH, but the release's `author` field still shows the bot. There is no `release.yml` workflow in this repo (no `.github/workflows/` files exist), so the auto-creation must be from a repo-level GitHub App or webhook. This is a pre-existing project behavior, not something I changed.
  6. **No `book-kit` engine-file allowlist bump for `book-kit/docs/TOOLKIT.md`.** If `book-kit/build_manifest.py` uses a hardcoded engine-file list, the new TOOLKIT.md + 18 new scripts may need to be added to it. The v1.1.0 release added 6 entries to the allowlist (`tests/*.py`, `pytest.ini`, `docs/WORKFLOW.md`, `docs/TRANSLATION_MODE.md`, `docs/SCRIPTS.md`); the v1.2.0 release adds many more files. **Surface to master for confirmation** — if a v1.2.0 kit ZIP is being built and shipped, the manifest needs to be updated; if v1.2.0 is just a tag for the controller, the kit ZIP can wait.
