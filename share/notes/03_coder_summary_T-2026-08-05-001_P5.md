## Known issues / TODOs left in code

These match the WARN-register patterns the dispatch asked me to surface. They are NOT bugs and NOT auto-fixed per the dispatch protocol:

- **LOW WARN candidate — `parse_rule_applicability` regex requires whitespace around `ch-NN`.** The regex `r"\|\s*([^|\n]+?)\s*\|\s*ch-(\d+)\s*\|"` requires `\s*` on both sides of the `ch-NN` cell. A markdown table row like `|Countdown ≥1|ch-03|Setup|—|` (no padding whitespace — rare in practice but legal) would not parse. The implementation tolerates extra whitespace, just not zero whitespace. Real-world writer-tool outputs (Obsidian, iA Writer, plain GFM) all use padded cells, so this is unlikely to bite. Fix would be 2-line: relax both `\s*` requirements to `*`. Not auto-fixed per dispatch.
- **LOW WARN candidate — `parse_rule_applicability` doesn't filter out the `Applies from` header cell.** The header row `| Rule | Applies from | Reason | Supersedes |` has 4 cells; the regex captures `Rule` (first cell) and tries to match `Applies from` against `ch-NN` (which fails), so the header row is naturally skipped by virtue of its second cell not containing `ch-NN`. No code change needed — documenting the property. The explicit `rule_name.lower() == "rule"` filter on line 230 is belt-and-suspenders against a future schema change where the header text varies.
- **LOW informational — `_resolve_config_paths` accepts any directory as a book root.** A user could point `--config` at any directory on disk; if neither `style-guide.md` nor `bible.md` exists there, both returns are None and the script falls back to defaults. This is graceful but doesn't enforce "this is a book root" (e.g. via a `chapters/` subdir check). Per dispatch, the contract is "graceful fall-through to defaults" — the absence of an enforcement check is by design, not a bug.
- **Informational — no `--task` flag impact.** P5 didn't add any new CLI flags; the existing `--config` / `--json` / `--task` / `--report-dir` flags are unchanged in semantics. The orchestrator's existing dispatches (Phase 6 chapter-write gate + Phase 7 review) need to be updated to pass `--config <book-root>` instead of `--config <style-guide.md>`; that is a master/orchestrator concern, not P5, and is out of scope here.
- **Informational — `parse_rule_applicability` doesn't surface warnings on malformed rows.** If a row has `ch-XX` (non-numeric) the regex silently skips it. A future P8 caller that wants to validate the table before trusting it would need an `errors=` return path or a `validate_only` mode. P5's contract is "best-effort parse; fall back to defaults on any problem" — strict validation is a separate concern.
