## API style decision
- `import pymupdf as fitz` (line 71) — recommended by dispatch and by the PyMuPDF 1.28 deprecation notice. The `fitz` alias keeps the rest of the code (`fitz.open`, `fitz.FileDataError`) identical to the pre-1.28 idiom, so the script reads naturally for anyone familiar with PyMuPDF. The docstring documents this choice explicitly so future maintainers don't "fix" it back to `import fitz`.

## Suggested review focus
- **Widow/orphan heuristic (page-level, heuristic)** — the spec explicitly says "rough heuristic" and "may need tuning". My implementation uses top/bottom 20% thresholds + 1/3 page width ceiling, matching the plan's literal description ("last line of para < 1/3 page width"). A real typesetting-perfect detector would need paragraph-reconstruction across page boundaries, which PyMuPDF does not expose; that's a future P13.x if the project needs it.
- **Path validation against PDF parent dir (not book root)** — P11/P12 used `--book <book-root>` and validated writable paths against the book root. P13 takes `<book.pdf>` and validates against the PDF's parent directory (the only natural "root" when no `--book` is supplied). The compensating control here is that the orchestrator's Phase 7 paragraph hardcodes `<book>/exports/book.pdf` and `<book>/figures/...`, so production stays within the book root in practice.
- **Fixture PDF generation in `tmp_path`** — every test builds its PDF programmatically with `pymupdf.open()` + `page.new_page()` + `page.insert_text()`. No binary fixtures in the repo. The trade-off: tests depend on PyMuPDF's default font (Helvetica) producing the expected bbox widths; a future PyMuPDF default-font change could shift the heuristic thresholds. Acceptable for a heuristic; documented in test docstrings.
- **`page.search_for()` semantics** — uses PyMuPDF's built-in search which is reliable for ASCII and Unicode (verified with the "Chapter 1/2/3" smoke). A regex-based marker matcher would be more flexible but is YAGNI for the current scope.
