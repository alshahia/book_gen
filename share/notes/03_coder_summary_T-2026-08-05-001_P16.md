## Bug found and fixed during the run: `render-examples.sh` shipped broken output at exit 0

Worth reading, because it nearly shipped silently.

I rendered the first PDF batch via PowerShell, then ran the committed shell
script for real so the committed PDFs would genuinely be produced by the
committed script. The script reported success:

```
render-examples.sh: done
exit=0
```

The re-verification showed all 10 PDFs were **garbage**: 1 page, 94 characters,
`ar=0`, zero Arabic.

Root cause: under Git Bash the script sees a POSIX path
(`/e/book_gen/book-kit/examples/x.html`). Chrome is a native Windows binary and
cannot resolve `file:///e/book_gen/...`, so it rendered *its own error page*
and exited 0. Chrome's exit code does not report input-load failure.

Two fixes:

1. `to_file_uri()` converts via `cygpath -m` when available, producing
   `file:///E:/book_gen/...`, and falls back to `file://` elsewhere.
2. A `MIN_PDF_BYTES=20000` post-render guard. A real sample is ~80 KB; an
   error page is ~14 KB. Any PDF that is missing or implausibly small now
   fails loudly with exit 3.

Verified the guard fires: a near-empty input produced `14362B (< 20000B)` and
exit 3. The committed PDFs were then re-rendered by the fixed script and
re-verified.

Had I trusted exit 0, this commit would have shipped 10 broken PDFs whose
`%PDF-` magic bytes and PyMuPDF parse would both have passed a naive check.
