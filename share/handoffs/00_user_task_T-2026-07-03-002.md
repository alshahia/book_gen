## Locked design decisions (from brainstorming + Q&A)

1. **Memory visibility: Hybrid (shipped scaffold + local writable).**
   - The empty folder structure, schema docs, README, and `.gitkeep` files ship in the repo.
   - Populated memory content (the actual semantic/episodic files) is gitignored — each operator's clone fills its own.
   - Rationale: downstream users inherit the scaffold; operators customize per install; sensitive runtime notes don't leak across clones.

2. **Memory scope model: Three scopes — global + project + role.**
   - `agents_manager/memory/global/` — cross-project facts. Owned by master.
   - `agents_manager/memory/projects/<slug>/` — per-project knowledge. Owned by master. Default slug = directory basename (`context_gen`); override via `agents_manager/.active-project`.
   - `agents_manager/<role>/notes/{semantic,episodic}/` — per-role expertise. Owned by that specialist. Uses the **existing declared structure** (every SKILL.md already declares its folder as memory) — empty until populated.
   - Read order: global → project → role (highest-leverage first).

3. **Write authority: Hybrid — specialists write role-scope; master writes project-scope and global-scope.**
   - Each specialist owns and writes its own `agents_manager/<role>/notes/`.
   - Master writes both `memory/global/` and `memory/projects/<slug>/`.
   - Master's own "role-scope" memory collapses into `memory/global/` (master IS the orchestrator; its accumulated lessons are inherently cross-project).
   - Write-on-exit protocol: every dispatch contract gains a mandatory `Memory written: <path>` (or `No memory write: <reason>`) line.

4. **File schema (single template, three scopes):**
   - Frontmatter: `scope: global|project|role`, `topic:`, `status: active|superseded`, `superseded_by:`, `created:`, `last_verified:`
   - Body: TL;DR + Context + Insight + Source + Verification (the last is what makes memory trustworthy).

5. **Lifecycle:** append-only content; supersession via `status: superseded` + `superseded_by:` link; master sweeps at Phase 5 close for entries with `last_verified > 90 days` (flag, don't auto-delete).

6. **Read budget:** each specialist reads ≤200 lines per scope on entry; grep for current task keyword if files are large.

7. **CHANGELOG/version:** this is a meaningful capability — version bump to v0.13.0 (since v0.12.0 was just shipped in T-2026-07-03-001).

## Phase 1 (research) — additional locked decisions

Surface by am-research after validating the initial 7. Confirmed 2026-07-03:

8. **`scripts/validate-memory.sh` ships in v0.13.0 (REQUIRED, not optional).** Acceptance criterion #11 promoted from "optional" → hard requirement. ~50 LOC bash. Checks: frontmatter has required keys (`scope`, `topic`, `status`, `created`, `last_verified`); `status` ∈ {active, superseded}; `scope` ∈ {global, project, role}; `superseded_by:` resolves to an existing file (when present); `created` and `last_verified` parse as YYYY-MM-DD. Failure mode without it: broken `superseded_by:` links silently mislead readers.

9. **`agents_manager/.active-project` uses YAML front-matter.** Format:
   ```yaml
   ---
   slug: context_gen
   aliases: [agents-manager, controller]
   description: The agents_manager multi-agent orchestration controller
   ---
   ```
   `slug:` is required; `aliases:` and `description:` optional. Default (when file absent) = `basename $PWD`. Validator must parse YAML and require `slug:` matching `^[a-z0-9_-]+$`. The file itself is gitignored.

10. **Master's re-entry reads (a) `memory/global/` + (b) `memory/projects/<active-slug>/` + (c) `share/notes/99_progress_<task-id>.md`.** Three sources, same 200-line cap each as specialists. Master's own "role-scope" memory collapses into `memory/global/`.

11. **Assets specialist gets a fresh `agents_manager/assets/notes/{semantic,episodic}/` tree** alongside the existing `agents_manager/assets/notes/branch-decisions.md` (which has a different append-only lifecycle and is preserved). Per-role `notes/README.md` for am-assets documents both.

12. **Co-exist migration stance.** Scaffold is purely additive. New `.gitkeep` and README files land only where the folder is empty. Existing operator content stays put. Documented in CHANGELOG entry. No content relocation.

13. **Secrets-free memory.** Memory entries must never name, quote, or reference a `share/notes/02_secrets_<task-id>.md` path or value. Reference the task id (`T-2026-XX-XX-NNN`) instead. Same rule as CHANGELOG entries.

## Research-baked protocol additions (locked from recommendations)

- **Memory entry size cap:** ≤20 lines per entry. Embedded in canonical `agents_manager/memory/README.md`.
- **"Durable insight" criteria** (testable, embedded in canonical README):
  1. Would a different agent (or me, in 3 months) benefit from knowing this on re-entry? (Yes → write.)
  2. Is it derivable from `share/notes/03_coder_summary_*.md` or the source code? (Yes → don't write; cite the source instead.)
  3. Did I spend >30 seconds figuring it out, or did it contradict my prior expectation? (Yes to either → write.)
- **Do NOT write into `templates/<name>/memory/`.** That's the template author's lane (`agents_manager/assets/SKILL.md:80`). Memory scaffold explicitly fences this.
- **Per-role `notes/README.md`** is a 2-line pointer to the canonical `agents_manager/memory/README.md` (not a duplicate of the schema). Reduces schema-drift risk.
- **CHANGELOG entry** follows v0.12.0 template (`agents_manager/CHANGELOG.md:9-43`): "What's new" / "Why" / "Files touched".
- **90-day sweep at Phase 5 close** — master sweeps memory entries with `last_verified` older than 90 days; flags them in the WARN register; does not auto-delete.
- **Substantive-vs-trivial dispatch distinction** — master only gates on `Memory written:` line for dispatches that hit `tasks/<id>.md` rows (real work). Trivial status checks can use `No memory write: trivial`.

## Risk register (initial — research may add more)

- **R1:** Specialists might silently ignore the "write-on-exit" protocol. → Mitigation: master gates on `Memory written:` line presence (warn if missing on substantive dispatches).
- **R2:** Memory files bloat over time. → Mitigation: 90-day `last_verified` sweep at Phase 5 close.
- **R3:** Master's project-slug detection picks the wrong slug. → Mitigation: explicit `agents_manager/.active-project` override file; Phase 0 stamps the chosen slug into `share/handoffs/00_user_task_<id>.md` for transparency.
- **R4:** Cross-project contamination if user runs agents_manager on multiple projects. → Mitigation: per-project scope is the default; global is intentionally narrow.
- **R5:** Schema drift across 7 specialists' READMEs. → Mitigation: copy one canonical template; specialists fill only the "what this role writes" section.
- **R6:** The task edits `agents_manager/SKILL.md` (master's own — within lane) AND `agents_manager/<role>/SKILL.md` (others — NOT within master's lane). → Mitigation: all `<role>/SKILL.md` edits go through am-coder per dispatch contract; master dispatches the changes.
